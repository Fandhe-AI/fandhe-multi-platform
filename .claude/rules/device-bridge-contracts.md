**本表を使う前に `AGENTS.md` を必ず読むこと。**

## 使う部品

request/response 型（要求 1 件を出して 1 件の結果を待つ橋渡し）は、同じ仕組みを新しく書かず
次を使う。

- Rust 側の要求追跡: `crates/fandhe-egui-proxy/src/device/request_slot.rs` の `RequestSlot` /
  `poll_and_finish`（#943）
- Android 側の要求 id 追跡: `platforms/android/app/src/main/java/com/fandhe/androidapp/RequestTracker.java`（#944）

継続配信型（location / gamepad / tilt のように結果が繰り返し届く機能）と camera は別型として扱う
（採用しない理由は各モジュールの doc コメントを参照）。

## チェック表

push 前に自己点検する。各項目は実装者が○×を付けられる問いにしてある。

### 1. ライフサイクル境界（46 件、file-picker → location → biometric → secure-credential で再発）

- Activity 再生成・`onPause` / `onDestroy`・bfcache 復帰で、保留中の要求をどうするか
  （破棄 / 永続化 / 確定）を決めて実装したか
- 切断・破棄後に、最後に届いた値を返し続けていないか
- 通知・オブザーバーの登録トークンを握り続けているか（ARC / Drop で即解放され、登録が無効になっていないか）
- 権限ダイアログの応答とライフサイクルイベント（`onPause` / 背景遷移 / Inactive）の到着順が入れ替わっても、正常な許可を中断扱いにせず、背景での録音開始も防いでいるか
- 同じ出来事から届く複数の通知（`visibilitychange` と wake lock の `release` 等）が逆順に届いても、
  保持中の参照の有無ではなく実際の状態（`released` 等）を見て判断しているか（screen-wake-lock #1297）
- リスナーの登録から参照の保存までの間に届いた通知を落としていないか（screen-wake-lock #1297）

### 2. 並行性・世代（42 件）

- 判定（現在の要求か・完了済みか）と状態更新は同じロックの内側で行っているか
- 起動済みの要求を二重にワーカーへ渡していないか
- 古い世代（キャンセル済み・差し替え済みの要求）の完了通知を照合して捨てているか
- 結果を届ける前に対応する状態を確定させているか（届けた後で片付ける順序になっていないか）
- `await` / 非同期コールバックの再開後に、要求がまだ現在のものかを再確認しているか
- 同じ要求の希望状態を複数箇所（画面側とドライバ側等）に持つとき、失敗・取り消し・解除失敗の確定で
  全箇所を同じ値へ揃えているか（screen-wake-lock #1297）
- 処理中（busy・保留中の Promise）に届いたイベントを黙って捨てず、完了時に現在の状態で一度評価し直しているか（screen-wake-lock #1297）

### 3. 期限・キャンセル（40 件）

- Rust 側の期限と OS 側の期限（UI キューでの遅延を含む）が一致しているか
- キャンセルが起動中の全ワーカーへ伝わるか
- 期限切れ・割り込みで失敗を確定した後に、UI キューへ投げた適用処理が走って OS の状態を変えていないか。
  開始済みで中断できないなら完了を待って実結果を返し、未開始なら開始と取り消しを排他にしているか（screen-wake-lock の Android #1290）
- 期限の起点を呼び出しの開始に取っているか。固定間隔の sleep で期限を超えて待っていないか。期限を過ぎてから届いた結果を成功として受け取っていないか（pedometer #1265）
- 期限・間隔・録画時間などの経過時間を、壁時計（`NSDate`・`Date::now()`・`SystemTime`）ではなく
  単調時計（`CACurrentMediaTime` / `mach_absolute_time`・`performance.now()`・`Instant`）で測っているか。
  システム時刻の変更で 0 や負の値にならないか（accessibility-prefs の Web #1324・screen-capture の macOS #1349）
- 期限切れ・キャンセルで戻る前に、登録したリスナー・非同期操作の解除が済んでいるか（UI キューへ解除を post しただけで戻っていないか。pedometer #1265）

### 4. ポーリング・再描画（16 件、location → text-scale → gamepad で再発）

- 送信を省略する分岐でも、pull 型は次回のポーリングを予約しているか
- 失敗状態のまま再描画し続けていないか
- iOS の delegate・completion（OS コールバック）が結果を共有状態へ入れた直後に、`crate::ios::request_repaint` で次フレームを起こしているか（入力がないと egui が描画せず、画面が処理中のまま止まる。calendar #1231・contacts #1232 で再発）

### 5. FFI 境界（15 件）

- Rust ワーカーからの Cocoa 呼び出しは `@autoreleasepool` の内側か
- UI を要する呼び出しは main queue で行っているか
- completion は一度きりしか呼ばれないか
- JNI の署名は Java 側・no-op スタブ・実体の 3 か所で一致しているか
- 値域・軸の向き・未取得の表現は両側（Rust / OS）で揃っているか。範囲の検証は丸め・変換の前に行っているか（power-state の Web #1296）
- OS 固有のエラーコード（HRESULT / NSError / 例外）を契約上のエラー種別へ、全呼び出し箇所で一貫して写像しているか
- 同じ意味のエラーコードが複数ある場合（CoreMotion の `CMErrorNotAuthorized` と
  `CMErrorMotionActivityNotAuthorized` 等）にすべて拾っているか。非同期の失敗経路で元のコードを
  `-1` 等へ潰していないか（pedometer の Windows #1257・iOS #1260）

### 6. 嘘の成功（10 件）

- 失敗・0 バイト・未接続・権限拒否を成功値へ畳んでいないか
- 初期化に失敗したとき、ダミー実装へ黙って倒していないか
- Mac 目視は正常系（外部コマンド・別アプリで OS と本当に連携しているか）と失敗系（OS 機能を
  切った状態で偽の成功が出ないか）の両方を行ったか。目視は実装 PR の push 前ではなく、
  実装ツリーの外の確認用 issue（expand-capability Step 7、`device-check-pending` ラベルの確認用 issue）で行う
- trait の doc に書いた契約（値域・未取得時の戻り値・`Unsupported` の条件）を各 OS 実装が
  守っているか、実装後に読み合わせたか

### 7. 対応表・権限（11 + 11 件）

- `impl` に書いたパスは実在するか
- 対象外の OS まで `done` にしていないか
- Android の `uses-permission` / `queries`、Apple の usage description を宣言したか
- 不要な権限を追加していないか
- 使用 API が対象 OS バージョン全域（Android は minSdk）で使えるか。使えない場合は API レベルで分岐したか
- `cfg` で OS 限定した定義を広げたとき、依存する import・static・関数の cfg も同じ OS 集合に揃えたか

### 8. 秘密値（6 件）

- 入力どおりに保存しているか（trim 等で前後の空白を意図せず除去していないか）
- 番兵値（未取得を表す特別な値）と実際の値域が衝突しないか
- ログへ出力していないか

### 9. 失敗時のリソース解放・共有状態復元（10 件、macOS → Windows → iOS → Web で再発）

- 開始・有効化に失敗した経路でも、確保済みの一時ファイル・ネイティブハンドル（`MediaCapture` 等）・共有セッションを解放しているか。
  画面ごとの起動記録（グローバルな登録表等）も、破棄・失敗の全経路で消しているか（power-state の Web #1296）
- 共有リソース（`AVAudioSession` の category / options 等）を変更する前の状態を保存し、失敗を含む全終了経路で復元しているか
- リスナー・タイマー・クロージャの登録に失敗した / 早期 return した場合も、既に確保した分を解放しているか（`forget()` で永続リークしていないか）。
  画面の破棄でも、`setTimeout` のハンドルを `clearTimeout` してからクロージャを drop しているか（power-state の Web #1296）

### 10. キャンセル・正常終了・失敗の三値（6 件、macOS → Windows → Android で再発）

- 利用者操作によるキャンセルや想定どおりの短時間終了を「失敗」として見せていないか
- 停止のタイミング（初期化中・0 バイト・自動停止）ごとに、成功 / キャンセル / 失敗のどれで報告するかを実装前に決め、doc に書いたか

### 11. 並行経路の集約と守備範囲（#1041・#1049〜#1052 の 30 件超）

- 画面・作業スレッド・OS コールバック・終了処理が同じ状態を触る機能は、受付を 1 本の直列キュー（`mpsc` + 専用スレッド、または OS の serial queue）に集約し、表示・非表示・発火・終了をそこへ順に流しているか。経路ごとに別のロックを足していないか
- 守る範囲（1 プロセス内の順序・嘘の成功の禁止・資源の解放）と守らない範囲（複数タブ・複数プロセス・同一ミリ秒・終了処理との重なり・OS 側の非同期確定との時間差で、表示が一時的に食い違うだけのもの。データの消失・資源の漏れ・嘘の成功は範囲外にできない）を、実装前に trait doc と対応表の `note` に書いたか（`AGENTS.md`「端末機能の並行性は守備範囲で判定する」）
- trait doc の契約を変えるときは、機能 PR に混ぜず先行する docs PR で main へ入れたか（自動レビューは base の文書しか根拠にしない）
- main thread へ `dispatch_sync` する呼び出しを、main 側も取るロックで囲んでいないか（デッドロックする）
- 取り消し・終了時の後片付けは、OS が代わりに片付ける場合（プロセス終了で `NSStatusItem` が消える等）を調べ、無理に同期させていないか
