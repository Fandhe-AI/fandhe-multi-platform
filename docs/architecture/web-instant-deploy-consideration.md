# Web 限定即時反映の技術検討記録

## 1. 目的・位置づけ

本書は REQ-16（`docs/spec/04-requirements.md` L204〜214）の受け入れ基準2項目目「Web（WASM）ターゲットに限り、
審査を経ない即時反映の技術的な可能性を Could 項目として記録する（PoC-6 では机上の推論にとどまり実装検証は
未実施）」に対応する TASK-16.2（`docs/spec/05-tasks.md` L479〜484、M6）の成果物です。

- **優先度は Could**: 本書は技術検討の記録であり、実装・実機検証を伴いません。Web 即時反映の実装着手は
  本書のスコープ外です（§5 参照）。
- **`docs/spec/` との関係**: `docs/spec/` は読み取り専用サブモジュールのため、本書は本リポジトリ側
  （`docs/architecture/`）の新規ドキュメントとして作成しています（`web-rendering-policy.md` /
  `state-access-api-tradeoff.md` / `build-and-sign-cli.md` と同じ置き場・体裁）。
- **対象とする変更**: 本書で「AI が生成した変更」と呼ぶのは、外部エージェントが `docs/ai/SCHEMA.md` を
  読んで `fandhe-core` の画面・状態コードを生成し、通常の開発フロー（人間レビュー・マージ）でリポジトリへ
  反映した変更を指します。生成主体・生成手段は特定しません。
- **関連文書**: iOS/Android のストア審査必須制約（TASK-16.1）は §2 に要約しています。あわせて
  PoC-6 README（`docs/spec/03-poc/ai-optimization/README.md` L89・L127・L133）を参照してください。

## 2. 前提整理

- **iOS**: OS のコード署名機構（Apple のコード署名・provisioning）が、署名されていないネイティブ実行
  コード（dylib・フレームワーク等）の実行自体を技術的に阻止します。これに加えて Apple Developer
  Program License Agreement §3.3.1(B)・App Store Review Guideline 2.5.2 が、審査を経ないコード配信を
  ストアポリシーとして禁止します。両者が独立に働くため、AI が生成した変更の反映には
  再ビルド・再署名・再審査が必須です。
- **Android**: OS 自体はネイティブコード（`.so` 等）の動的ロードを技術的には禁止していません。制約の
  出所は Google Play Developer Program Policy「Device and Network Abuse」で、Google Play からの
  配信を除き実行コード（dex・JAR・`.so` 等）のダウンロード・自己更新を禁止するストアポリシーです
  （<https://support.google.com/googleplay/android-developer/answer/9888379>）。本フレームワークの
  `fandhe-egui-proxy` cdylib（`.so`）はこのポリシーの対象に該当します。iOS と異なり OS 側の技術的な
  阻止機構ではなくストアポリシー由来の制約である点に注意してください。
  - 両プラットフォームとも、変更の反映には再ビルド・再署名・再審査が必須という結論自体は共通です
  （TASK-16.1 / Issue #276）。
- **Web**: `wasm32-unknown-unknown` ターゲットにはストア審査が存在しません。配信物は
  `scripts/web/build-wasm-proxy.sh` が組み立てる `crates/fandhe-egui-proxy/web/dist/`（`.wasm` +
  wasm-bindgen JS + `index.html` + フォント）であり、`scripts/web/serve-brotli.mjs` 相当の静的配信で
  成立します。この「審査が存在しない」性質が、Web 限定で即時反映を検討できる根拠です。
- **AI が生成した変更の反映経路の現状**: 生成 → 人間レビュー → マージというリポジトリへの反映までは
  通常の開発フローで成立しますが、その先の配信（デプロイ）工程は本リポジトリに存在しません。本書は
  この事実を出発点とし、以降の検討は生成手段の実装によらず成立する内容として扱います。

## 3. 技術的成立可能性の検討（机上）

本節はいずれも検討のみであり、実装・実測を伴いません。

### 3.1 パイプライン案

AI が生成した変更のマージ → `FANDHE_WASM_RELEASE=1 scripts/web/build-wasm-proxy.sh`（release +
`wasm-opt` 経路）→ dist を静的ホスティングへ配置、という流れであれば、成果物の組み立て自体は
既存スクリプトで成立します。ただし、この案には以下の工程が欠けています。

- **デプロイ**: dist をホスティング先へ転送・切替する仕組みが存在しません。
- **ロールバック**: 反映後に問題が生じた際、前バージョンへ戻す手順が存在しません。
- **配信物の署名検証**: 転送・配信経路の完全性を保証する仕組みが存在しません（§4 で採用条件として整理）。

### 3.2 反映単位・キャッシュ

`.wasm`・JS をハッシュ付きファイル名にする、または `Cache-Control` を適切に設計し、`index.html` の
差し替えで切替する方式が考えられます。ロールバックは前バージョンの dist を保持しておく運用が候補に
なります。

### 3.3 「即時」の意味

ストア審査の待ち時間（地域・アカウント・更新内容・時期により変動するため本書では具体的な日数を
保証値として示しません）が不要になる、という意味に限られます。`cargo build`（release + `wasm-opt`）
自体のビルド時間は残るため、具体的な短縮時間の数値は本書では示しません（未計測のため）。

### 3.4 制約

AI が生成した変更のリポジトリ反映に対する人間承認（レビュー・マージ）は、Web 即時反映の検討に
おいても必ず経由する前提とします。承認なしの自動配信は本書では採用候補としません。

## 4. セキュリティ要件（採用条件）

`.claude/rules/security.md` の A08 は現時点で「OTA 更新（Web 限定）は署名検証を必須とする」とのみ
定めています。本書はこの現行要件（署名検証）を Web 即時反映の採用条件の一つとしたうえで、あわせて
配信経路（オリジン・デプロイ資格情報）の侵害という脅威モデルへの対応として、独立した信頼アンカー・
配信経路侵害耐性・リプレイ耐性という**追加要件**を検討します。これらの追加要件は現行の
`.claude/rules/security.md` A08 の記述には含まれておらず、本書が独自に提案するものです（以下
「本書提案の追加要件」と呼びます）。**現行 A08 と本書提案の追加要件は、本書内で次のとおり明確に
分離して扱います**（正式採用の要否は §5 末尾で述べるとおり `.claude/rules/security.md` または
`docs/spec/` 側の検討事項とし、本書側で先取りして確定させません）:

- **現行 A08（署名検証必須。`.claude/rules/security.md` の記述どおり）**: manifest への署名・
  クライアント側での署名検証を指します。この検証自体は、検証コードがどの経路から配信されるかに
  よらず形式的に実行可能です。
- **本書提案の追加要件（未反映・提案段階）**: 検証コードそのものが検証対象と同じ配信経路（攻撃者が
  侵害しうる経路）から届く構成では、形式的な署名検証を実行していても攻撃者が検証コード自体を
  差し替えられるため、TLS（(c) 参照）を超える実質的な整合性保証にはならないという分析に基づき、
  「検証器・検証鍵を配信経路から独立させる」信頼アンカー要件（後述 (a) の (i)）、およびそれに伴う
  配信経路侵害耐性・リプレイ耐性を、A08 の実質化として本書が追加提案するものです。この追加要件は
  現行の `.claude/rules/security.md` A08 の記述そのものではなく、反映され正式採用されるまでは
  本書独自の提案にとどまります。

候補は以下のとおりです（いずれも検討のみで未実装）。

- **(a) 成果物ハッシュ manifest への署名と検証**: dist 成果物のハッシュ manifest に Ed25519 署名を行う。
  署名鍵は、リポジトリへの変更反映を承認・署名する鍵（コミット署名鍵等）とは独立した、配信専用の
  鍵系統とします。両者は利用主体（変更承認: 変更のリポジトリ反映可否を判断する運用者／配信署名: dist
  成果物の公開を行うデプロイ主体）・保管場所・ローテーション頻度が異なるセキュリティドメインであり、
  鍵を共用すると配信署名環境の侵害がリポジトリ変更の承認権限へ波及するなど影響範囲が不要に拡大する
  ためです。配信署名鍵は、変更承認鍵とは別の key ID・
  別の保管先（CI Secrets／キーチェーン）で管理し、失効・ローテーション手順も個別に定めます（具体的な鍵管理手順の
  策定自体は本書のスコープ外・着手時の実装課題とします）。`.claude/rules/security.md` の A08 は
  署名検証を必須とするため、生成（サーバー/CI 側での manifest 署名）だけでなく、以下のクライアント側
  検証工程を採用条件に含めます。
  - **信頼アンカーの限界と扱い**: 検証用公開鍵を `index.html` やブートストラップ JS に埋め込む方式は、
    その配布物自体が manifest・成果物と同じ Web デプロイ経路（同一ホスティング先・同一デプロイ資格
    情報）で更新されるため、ホスティング先やデプロイ資格情報を侵害した攻撃者は manifest・成果物と
    一緒に埋め込み公開鍵・検証コードも差し替え可能です。**公開鍵のみを別オリジンへ切り出しても
    この限界は解消しません**: 署名検証を実際に実行するコード（`index.html`・ブートストラップ JS）が
    引き続き侵害対象の Web デプロイ経路から配信されるため、攻撃者は鍵の取得先を変更するコードや、
    検証そのものを省略するコードへ差し替えられます。したがって、公開鍵の配置場所だけを条件にする
    方式は配信経路そのものの侵害に対しては、TLS（(c) 参照）が既に提供する転送経路上の改ざん検知を
    超える追加の保証を持ちません。**したがって、検証コードが配信経路から独立していない構成は、署名検証を
    形式的に実行していても本書提案の追加要件が求める実質的な整合性保証を満たしません。** この限界を
    踏まえ、「検証を実行するコード（検証器）自体」を配信経路外に固定する次の (i) を、本書提案の
    追加要件を実質的に充足するための必須条件とします（未実装・着手時の設計課題。通常のブラウザー配信
    の構成でこの条件を満たせるかどうかの判定は §5 で行います）。
    - **(i)（本書提案の追加要件を実質的に充足するための必須条件）**: 検証器（署名検証・ハッシュ照合を実行するコード
      そのもの）を Web デプロイ経路から独立して配布・実行する方式に限ります。該当するのはネイティブクライアント
      （iOS/Android アプリにあらかじめ組み込まれた検証コードが、Web デプロイ経路から取得した
      manifest・成果物を検証する構成）です。ブラウザーが独立して強制できる同等の信頼機構（例:
      ブラウザー標準機能によるコード署名の強制）が将来利用可能になった場合はそれも候補になり
      得ますが、通常の Web 初回ロード（`index.html` を Web デプロイ経路から取得して実行する構成）
      にはそのような機構は存在しないため、現状は候補になりません。**公開鍵のみを別オリジンに配置し、
      検証器自体は通常の Web デプロイ経路で配信する方式は、この条件を満たしません**（検証器を
      差し替えられれば鍵の配置場所は無関係になるため）。以下の「検証順序」「リプレイ（ロールバック
      攻撃）防止」の各記述は、この (i) の採用を前提として成立するものです（(i) を採用しない場合の
      扱いは §5 で判定します）。
    - **(ii)（不採用）**: 検証用公開鍵を `index.html` やブートストラップ JS に埋め込んで配布する
      方式、および公開鍵のみを別オリジンに切り出し検証器自体は通常の Web デプロイ経路で配信する
      方式は、いずれも検証を実行するコード自体が侵害対象の配信経路から配布されるため、TLS
      （HTTPS、(c) 参照）が既に提供する保証（転送経路上の改ざん検知）を超える整合性保証を追加
      しません。配信経路（オリジン・デプロイ資格情報）の侵害に対する独立した防御にはならないため、
      本書提案の追加要件を実質的に充足するための必須条件（(i)）としては選択可能な代替案とはせず除外します
      （不採用案として記録するのみとします）。
  - **検証順序**: (1) (i) の方式で配布された検証器・公開鍵で manifest 署名を検証 → (2) 検証成功後、
    manifest 記載のハッシュと
    ダウンロードした各成果物（`.wasm`・JS・フォント等）のハッシュを突き合わせ、の順で行います。manifest
    署名が先である理由は、ハッシュ一覧そのものが manifest 内にあり、署名未検証のハッシュ一覧を信頼して
    先に成果物を照合すると manifest ごと差し替えられた偽の一致を検出できないためです。**この順序が
    意味を持つのは、(1) を実行する検証器・公開鍵自体が (i) の方式（配信経路外での配布）で届いている
    場合に限られます。** 検証器が manifest・成果物と同じ Web デプロイ経路で配信される通常のブラウザー
    配信では、上記「信頼アンカーの限界と扱い」で述べたとおり検証器自体も攻撃者に差し替えられうるため、
    この検証順序を実行しても TLS（(c) 参照）が既に提供する転送経路上の改ざん検知を超える保証にはなりません。
  - **リプレイ（ロールバック攻撃）防止**: 署名・ハッシュ検証のみでは、攻撃者が正当に署名済みの旧
    manifest・旧成果物一式を再配信すること（既知の脆弱性を含む旧バージョンへ意図的に戻す攻撃）を検出
    できません。この検証順序（署名検証 → ハッシュ照合）は改ざんの検出であり版の新旧は判定しないためです。
    manifest 契約に以下を追加し、正当な署名があっても旧版を拒否できるようにします。
    - **単調増加するリリース番号**: manifest に単調増加する `release_number`（整数）を含め、署名対象
      に含めます。クライアントは直前に検証済みの `release_number` **未満**の manifest を、署名が
      有効でも拒否します。`release_number` が直前の検証済み値と**同値**の manifest は、再起動・
      再読込・キャッシュ消失後に同一の正規リリースを再検証する正当なケースであるため、ハッシュが
      直前の検証済み値と一致することを条件に許可します（一致しない場合は同一 `release_number` の
      詐称・改ざんとして拒否します）。拒否対象はあくまで直前の検証済み値**未満**への引き下げ
      （意図的ロールバック攻撃）です。§3.2 の前バージョンへの意図的ロールバック（既知の脆弱性を含まない
      旧バージョンへ運用上戻す場合）は、旧 dist をそのまま古い `release_number` で再配布すると本項の
      チェックで拒否されるため、旧成果物を新しい `release_number` を付与した署名済み manifest として
      再発行する契約とします（直前の検証済み値はロールバック不可能な形でクライアント側に保持する
      必要があります。**通常のブラウザー配信が使える永続化手段（`localStorage`・IndexedDB 等）は
      サイトデータ消去で失われるため、この「ロールバック不可能な保持」は通常のブラウザー配信単体
      では成立しません**。(i) のネイティブクライアント検証器が持つ独自の永続化領域を使うか、
      クライアントから独立した新鮮性の信頼源（サーバー側の透明性ログを毎回問い合わせる方式等）が
      必要ですが、いずれも未検討・着手時の設計課題です）。
    - **署名対象の有効期限**: manifest に有効期限（発行から一定時間、具体値は着手時に定める）を含め、
      署名対象に含めます。期限切れの manifest は署名が有効でも拒否します。
    - **検証器側の最低許容バージョン**: 検証器（§4(a)(i)）が受理する `release_number` の下限を、
      既知の脆弱性を持つ旧版を締め出すために更新可能な形で持ちます（更新経路は鍵ローテーションと
      同様、検証器自体の配信経路＝ネイティブクライアント更新を通じて行い、OTA 的な即時差し替えは
      設けません）。
  - **fail-closed 動作**: 署名検証・ハッシュ照合・リプレイ防止チェック（release_number・有効期限・
    最低許容バージョン）のいずれかが失敗した場合、新しい成果物の読み込み・切替を拒否し、直前に検証済み
    の現行バージョンを維持します（§3.2 の「保持済み前バージョンへのフォールバック」運用を、検証失敗時
    にも同一の仕組みとして適用する想定です）。
  - **鍵ローテーション**: 検証用公開鍵の更新は、旧鍵で署名した manifest が新鍵配布後も一定期間検証できる
    よう新旧鍵を並行受理する移行期間を設け、クライアント側の鍵埋め込みが更新された後に旧鍵を失効させます。
    **この鍵埋め込みの更新自体も (i) の検証器と同じ独立経路（署名済みネイティブアプリ更新）でのみ行い、
    Web デプロイ経路では更新しません。** Web デプロイ経路で鍵埋め込みを更新できてしまうと、その経路を
    侵害した攻撃者が新しい鍵を注入でき、(i) が前提とする「検証器・検証鍵が配信経路から独立している」
    という信頼アンカーが崩れ、fail-closed な署名検証が迂回されるためです。通常のブラウザー配信には
    (i) に相当する独立経路が存在しないため、この鍵ローテーション契約自体を実行する手段がなく、§5 で
    判定するとおり軸 B（配信経路侵害耐性）の未充足項目の一つとして扱います。
- **(b) SRI + CSP**: `<script>` 等の HTML 要素には Subresource Integrity（`integrity` 属性）を、
  `fetch` には同等の完全性検証として `RequestInit.integrity` オプション（`fetch` に `integrity`
  という HTML 属性は存在しないため区別する）を適用し、あわせて Content-Security-Policy を適用する。
- **(c) HTTPS 前提**: 配信経路は TLS を前提とします（`.claude/rules/security.md` A02 準拠）。
- **(d) 配信鍵の管理**: デプロイ鍵・ホスティング認証情報は CI Secrets
  またはキーチェーン経由でのみ参照します。

## 5. 判定と扱い

本節は §1〜4 の対象を、REQ-16 が想定する「通常のブラウザー向け Web 配信」（ネイティブアプリを介さず
ブラウザーが `index.html` を Web デプロイ経路から取得して実行する一般的な構成）に限定して判定します。

§4 で分離したとおり、現行 A08（`.claude/rules/security.md` の記述である署名検証必須）と、本書提案の
追加要件（検証器・検証鍵の配信経路からの独立、配信経路侵害耐性、リプレイ耐性）は別物です。

- **現行 A08（署名検証必須）**: manifest 署名・クライアント側検証という形式面は通常のブラウザー配信
  でも実装可能であり、現行 A08 の記述単体は充足しえます。
- **本書提案の追加要件**: 通常のブラウザー配信の構成では、次の 2 点の理由により実質的に充足できない
  と判定します。

- **検証器自体が同一配信経路で配布される（配信経路侵害耐性が満たせない）**: §4(a)「信頼アンカーの
  限界と扱い」で分析したとおり、通常のブラウザー配信では manifest 署名を検証するコード
  （`index.html`・ブートストラップ JS）自体が manifest・成果物と同じ Web デプロイ経路で配信されます。
  配信経路（オリジン・デプロイ資格情報）を侵害した攻撃者は検証コード自体を差し替えられるため、
  §4(a)「検証順序」に記載の署名検証・ハッシュ照合を実行しても、TLS（§4(c)）が既に提供する転送経路上
  の改ざん検知を超える保証は得られません。これを解消するには §4(a)(i) の独立した検証器（現状の候補は
  ネイティブクライアント組み込みのみ）が必要ですが、REQ-16 が想定する通常のブラウザー配信の構成には
  存在しません。
- **リプレイ防止に必要な状態保持が通常のブラウザーでは成立しない（リプレイ耐性が満たせない）**:
  §4(a)「リプレイ（ロールバック攻撃）防止」の `release_number` 単調増加チェックは、直前に検証済みの
  `release_number` を「ロールバック不可能な形」でクライアント側に保持できることが前提です。通常の
  ブラウザーが使える永続化手段（`localStorage`・IndexedDB 等）はサイトデータ消去で失われるため、
  攻撃者はサイトデータを消去させた被害者に対して、正当に署名済みの旧 manifest・旧成果物一式を
  再提示できます。クライアントから独立した新鮮性の信頼源（サーバー側の透明性ログを毎回問い合わせる
  方式等）が必要ですが、これも未検討・着手時の設計課題であり、通常のブラウザー配信の構成には現状
  存在しません。

したがって、§4(a)(i) の独立した検証器（配信経路外に固定された検証器・その独自の永続化領域）を
採用しない限り、通常のブラウザー配信の構成では本書提案の追加要件（信頼アンカー・配信経路侵害耐性・
リプレイ耐性）を実質的に充足できません（未実装・未実測での机上判断であり、将来ブラウザー標準機能等
で状況が変わる可能性は残ります）。**この追加要件は現行の `.claude/rules/security.md` A08 の記述には
含まれておらず、本書独自の提案です。** 追加要件を正式な採用条件とするには、`.claude/rules/security.md`
の A08 の記述として明示するか、関連仕様（`docs/spec/`）側への追加要件とするかを、`docs/spec/` の
変更要否も含めユーザー・spec リポジトリ側で先に決定する必要があります。本書は、上記の分析
（配信経路侵害耐性・リプレイ耐性が満たせないという整合性上のリスク）を理由に、**追加要件を満たさない
限り Web 限定即時反映を採用しない、という本書独自の保守的な立場**を
§5 末尾の結論で採ります（現行 A08 単体への違反ではなく、本書が採用条件として上乗せする追加提案に
基づく判定である点に注意してください）。

**ネイティブクライアント（iOS/Android アプリ）に検証器を組み込み、Web デプロイ経路から取得した
manifest・`.wasm` を検証・実行する構成については、本書の結論からは除外します。** この構成は §4(a)(i)
の独立した検証器としての要件（配信経路侵害耐性）そのものは満たしえますが、検証済みとはいえダウンロードした `.wasm`
をストア審査済みのネイティブアプリ内で新たに実行する行為は、§2 に整理した制約（iOS はコード署名機構による
技術的な阻止に加え Apple Developer Program License Agreement §3.3.1(B)・App Store Review
Guideline 2.5.2、Android は Google Play Developer Program Policy「Device and Network Abuse」）が
対象とする行為と同種であり、署名・ハッシュ検証はこれらの技術的阻止・ストア規約上の制約のいずれも
解除しません。この構成がストア審査を経ずに許容されるかは、`.wasm` をインタプリタ実行するランタイムに
対する例外規定の有無を含め別途ストア規約上の根拠を示す必要があり、本書ではその根拠を示せません。
したがって、この構成について「Web 限定の即時反映が技術的に成立しうる」と結論づけることはできず、
不採用案（着手時にストア規約上の根拠検証が別途必要な未解決の選択肢）として記録するにとどめます。

以上より、本書が示す範囲では、REQ-16 が想定する Web 限定即時反映（ストア審査を経ない反映）について、
通常のブラウザー配信の構成では本書が採用条件に含めた要件（現行 A08 の署名検証必須に加え、本書提案の
追加要件である信頼アンカー・配信経路侵害耐性・リプレイ耐性）を実質的に充足する手段を確認できておらず
（上記 2 点の理由）、これを満たしうる唯一の候補である独立検証器構成（§4(a)(i)、ネイティブクライアント
組み込み）はストア規約上の位置づけが未確立で本書の結論からは除外しています。本書の判定では、
本書が採用条件とする要件（現行 A08 に加え本書提案の追加要件を含む）を満たす形での Web 限定即時反映が
技術的に成立するとは判定できません。
技術的成立可否を将来確定させるには、独立した信頼アンカー・新鮮性の信頼源の具体設計
（ユーザー・spec リポジトリ側での検討を含む）に加え、実装・実測に
よる検証が必要です。実装着手は別 Issue の起票と、REQ-16 の Must（審査経由の明記等）が未達でないこと、
上記未解決の設計課題の解消、およびネイティブクライアント構成を採用する場合はストア規約上の根拠を
別途確立することを条件とし、**v1 スコープ外（Could）**とします。

着手する場合に必要となる作業（本書のスコープ外）:

- デプロイスクリプト（dist のホスティング先への配置・切替）
- 署名 manifest の生成・クライアント側検証工程の実装（§4 (a)。検証器（ネイティブクライアント組み込み
  検証コード等）を配信経路外に固定する方式の設計・公開鍵配布・検証順序・リプレイ防止（release_number・
  有効期限・最低許容バージョン）・fail-closed 動作・鍵ローテーション運用を含む）
- ロールバック手順の実装
- 実機・実配信の検証
