## 2. 前提となる既存実装の整理

設計方針は `crates/fandhe-core` の既存実装（TASK-1.1・TASK-8.3 系列）を土台とする。新規に導入する概念は
最小限に抑え、既存の型・走査 API を再利用する。

- **ツリー構造**: `Screen<S>` はトップレベル `Node<S>` の列を保持し（`crates/fandhe-core/src/ui/screen.rs`）、
  `Node::List` / `Node::VirtualList` は状態 `S` に応じて子ノードを動的展開する
  （`crates/fandhe-core/src/ui/node.rs` `expand_children`）。
- **path によるノード addressing（Issue #491 で確立済み）**: `crates/fandhe-core/src/ui/event.rs` の
  `click_button_at(screen, path: &[usize], label, state)` は、`path[0]` をトップレベル挿入順 index、以降の
  セグメントを `List::expand(state)` の列挙 index／`VirtualList` の絶対項目 index として反復的に降下し、
  対象ノードの `on_click` を発火する。降下は再帰を使わず反復ループで行い、`VirtualList` は該当 index の
  `item(state, index)` のみを 1 回呼ぶ（全展開しない、仮想化維持）。**本書が設計するフォーカス移動は、
  この既存 path 機構をそのまま「フォーカス可能ノードの識別子」として再利用する**（3 節参照）。
- **ウィジェット共通トレイトと `InteractionState`**: `crates/fandhe-core/src/ui/widget.rs` は
  `Widget<S>` トレイト（`interaction_state()` で現在の hover/pressed/disabled/focused を返す）と
  `InteractionState { focused: bool, .. }` を既に持つ（TASK-8.3-S2）。`InteractionInput::FocusGained` /
  `FocusLost` による状態遷移も実装済みだが、**「ツリー上のどの 1 ノードが現在フォーカスを持つか」を
  中央管理する仕組みはまだ存在しない**（各ウィジェットが自身の `focused: bool` を持つのみで、フォーカスの
  受け渡し・移動ロジックは未実装）。本書はこの空白を埋める設計を行う。なお現行 `Widget<S>` トレイトには
  Action/Input カテゴリ（決定ボタン押下が意味を持つ種別）と Display/Container カテゴリ（レイアウト専用・
  表示専用）を判別する API が存在しない（`interaction_state().disabled` は無効化状態を示すのみで、
  カテゴリ判別には使えない）。この制約は 3.1 節の定義判断に直結する。
- **VirtualList の仮想化契約**: `crates/fandhe-core/src/ui/node.rs` の `Node::VirtualList` は
  `len`（総項目数取得）と `item`（index からの単項目生成）のみを公開する。
  `crates/fandhe-core/src/ui/screen.rs` の `Screen::visit_windowed` はこの契約を活かし、可視範囲
  index のみへ `item(state, index)` を呼び出すことで仮想化（大規模リストでの毎フレーム全展開回避、
  TASK-5.5-S2）を実現する。一方 `Node::expand_children` / `Screen::visit_expanded` は既存の描画・
  スナップショット走査経路の意味論的後方互換を優先し `0..len(state)` を全展開するが、これは性能契約を
  持たない経路である（`node.rs` のモジュール doc 参照）。**本書が設計する `FocusRing` は
  `visit_windowed` と同じ「`len` で件数を把握し、`item` は必要な index のみ呼ぶ」性能契約に従う**
  （4.4 節）。
- **レイアウト情報の不在**: `crates/fandhe-core` には座標・矩形（`Rect` 相当）を持つ型が存在しない。
  `widget.rs` の `Measurement` は「幅・高さ」のみのプレースホルダで、位置情報（原点座標）は `Widget::paint`
  の引数としてレンダラ側から渡されるのみであり、共通コア側は保持しない。この制約は 4 節の設計判断に直結する。
  **なお本書が 4 節で新たに導入する `Axis`（配置軸の宣言）は「実描画後の矩形」とは別種の情報である**点に
  注意する。`Axis` は開発者が `Node::List`/`Node::VirtualList` を宣言する時点で明示的に指定する意味情報
  （縦一列か横一列かグリッド列数か）であり、実測ジオメトリの計算・保持を一切必要としない。共通コアが
  「レイアウト・描画呼び出し」の責務境界（`responsibility-boundary.md` 3 節）を超えて実描画後のジオメトリを
  把握する必要はなく、本段落の制約と矛盾しない（4.2 節で詳述）。
- **フォーカス可能ノードに安定した識別子がない**: `Node::Button` / `Node::IndexedButton`（3.1 節で
  フォーカス可能と定義する 2 バリアント）は現状 `label: String` のみを識別情報として持つ。ラベルは
  兄弟間で一意である保証がなく、表示文言の変更や項目の挿入・削除・並べ替えで「同じ path が別の論理項目を
  指す」状況を label だけでは判別できない。一方 `Node::Widget` 系列（`.label()` / `.checkbox()` /
  `.radio_button()` 等、TASK-8.3-S2 以降）はすでに `WidgetId`（`widget.rs`、`u64` ラップの
  `Copy + Eq + Hash` な一意識別子で `Screen` 構築時に開発者が明示的に割り当てる）を持つ。**本書は
  この既存の `WidgetId` の考え方を `Node::Button` / `Node::IndexedButton` へ拡張し、フォーカス可能な
  全ノードが安定識別子を持つ状態に揃える**（3.1 節・4.3 節）。これは新規の識別子体系を持ち込むのではなく、
  既存パターンの適用範囲を広げる設計判断である。

## 3. フォーカス可能ノードの定義とツリー内での探索順序

### 3.1 フォーカス可能ノードの定義

以下の条件をすべて満たす `Node<S>` を「フォーカス可能」と定義する（v1 スコープ。除外対象と理由は
下記参照）。

- **`Node::Button` または `Node::IndexedButton` であること**。決定ボタン押下時に 5 節の
  `activate_focus_at`（`click_button_at` の id 版、5 節参照）がそのまま解決できる葉ノードに限定する。
- `Node::Text` / `Node::List` / `Node::VirtualList` 自身（コンテナ・静的テキスト）はフォーカス不可とする。
  ただし `List` / `VirtualList` の**展開結果の子ノード**は、上記条件（`Button`/`IndexedButton`）を
  満たせばフォーカス可能である。

**型変更**: `Node::Button` / `Node::IndexedButton` へ
`id: super::widget::WidgetId` フィールドを追加する。既存の `Node::Widget` 系ビルダー
（`.label(id, get)` 等）とまったく同じ「開発者が `Screen` 構築時に一意な `WidgetId` を明示的に割り当てる」
契約であり、新規の識別子体系ではない（2 節）。

```rust
// node.rs（既存 2 バリアントへの追加フィールド。手動 Clone/Debug 実装への追随が必要）
Button {
    label: String,
    on_click: fn(&mut S),
    /// フォーカス識別・決定操作の安定識別子（本書で追加）。
    /// `label` と異なり表示文言の変更や兄弟間の重複を許容しない一意性を開発者側が
    /// 保証する契約（`WidgetId` 既存の運用と同一、`widget.rs` 参照）。
    id: super::widget::WidgetId,
}
IndexedButton {
    label: String,
    index: usize,
    on_click: crate::state::WriteFn<S, usize>,
    /// `List::expand` / `VirtualList::item` の生成元が割り当てる。**項目の並び順
    /// （`index`）ではなく、項目が表すデータの永続的な同一性から採番する**ことを
    /// 強く推奨する（例: `WidgetId::from_raw(item.id)`）。`index` は挿入・削除で
    /// シフトし得るため識別子として使うと 4.3 節が解決しようとしている問題を
    /// 再生産してしまう（4.3 節「id による二層検証」参照）。
    id: super::widget::WidgetId,
}
```

`Screen::button()` ビルダーは他のウィジェット系ビルダー（`.checkbox(id, ..)` 等）と対称になるよう
`pub fn button(self, id: WidgetId, label: impl Into<String>, on_click: fn(&mut S)) -> Self` へ
シグネチャ変更する（引数追加、破壊的変更）。`Node::IndexedButton` 専用のビルダーメソッドは元々存在せず
（`List::expand` / `VirtualList::item` の関数ポインタ内で直接 `Node::IndexedButton { .. }` を構築する
既存パターン、`event.rs` のテスト参照）、`id` フィールド追加は各アプリの生成関数側の変更で完結する。

**移行コストの見積り（TASK-17.2 実装時の前提作業）**: `crates/fandhe-core` 内に
`Node::Button { .. }` リテラルが 16 箇所、`Node::IndexedButton { .. }` リテラルが 13 箇所、
`.button(..)` 呼び出しが 82 箇所存在する（`sample.rs` 等の既存サンプル・テストを含む）。いずれも
コンパイラのフィールド不足・引数不足エラーが機械的に指し示す修正であり、意味的判断を要しない
（型不整合をコンパイル時に検出できる Rust の型安全性がそのまま移行の安全網になる）。TASK-17.2 の
着手時に、この移行をフォーカス機能本体の実装に先立つ前提ステップとして計画すること（8 節）。

この定義は「葉ノード（Button/IndexedButton）」の集合という点では従来と変わらず、新規の Node バリアントは
追加しない。

**v1 スコープから除外する対象と理由**（TASK-17.1 は「実装方針設計」であり、スコープを不必要に広げない
判断も設計判断のうちと位置づける）:

- **`Node::TextField`**: 決定ボタンによる選択ではなく、フォーカス後にテキスト入力を受け付ける
  別種の操作契約を持つ。IME 合成（`docs/architecture/ime-architecture.md`）を含む入力配線は、
  本書が扱う「上下左右のフォーカス移動・決定ボタンでの選択」（REQ-17 受け入れ基準）とは別軸であり、
  5 節の `click_button_at` 経路にも接続できない。対象外として切り出す（7 節）。
- **`Node::Widget`（`disabled: false` のもの）**: 2 節で述べた通り、現行 `Widget<S>` トレイト
  （`crates/fandhe-core/src/ui/widget.rs`）には Action/Input カテゴリと Display/Container カテゴリを
  判別する API が存在しない。`interaction_state().disabled == false` だけでは `AccessibilityRole::Group`
  （レイアウト専用コンテナ）や `AccessibilityRole::Image`（表示専用）といった非操作系ウィジェットも
  除外できず、フォーカスがこれらへ迷い込み決定ボタンが無反応になる契約不整合を生む。
  カテゴリ判別 API・決定ボタン発火契約の追加は、`Widget<S>` トレイト全体のイベントディスパッチ基盤
  （`event.rs` 冒頭コメントが言及する未着手事項）と合わせて設計すべき事項であり、対象外として
  切り出す（7 節）。

### 3.2 ツリー内での探索順序

フォーカス可能ノードの列挙**順序**（規約）は、**`Screen::visit_expanded` と同一の深さ優先・挿入順
（DOM 風の tree order）**とする。すなわち、トップレベル `Node` を挿入順に走査し、`List` /
`VirtualList` に遭遇した場合はその場で子へ descend する（`List` は `expand(state)` の列挙順、
`VirtualList` は `0..len(state)` の昇順）。

- 各フォーカス可能ノードは `click_button_at` が受け取る `path: &[usize]` とまったく同じ意味論の
  path（`Vec<usize>`）で識別する。ただし **`FocusRing` はこの path 列をツリー全体にわたって
  事前列挙・保持しない**。本節が定義するのはあくまで「列挙したとすれば得られる順序」という規約であり、
  実際の移動先解決は現在位置の近傍のみを都度辿ることで行う（4.4 節「列挙・移動解決の性能契約」）。
- 列挙順序は状態 `S` に依存する（`List::expand` / `VirtualList::item` が状態を参照するため）。したがって
  フォーカス可能ノードの集合・順序は状態更新のたびに変わり得る前提とする（4.3 節「状態変化時の再解決」）。
  **path は「ツリー上の位置」を指すだけで「論理的に同一の項目」を指し続ける保証はない**点に注意する
  （4.3 節が定義する `FocusEntry`・再解決契約はこの前提を踏まえた設計になっている）。

## 4. 方向キーによるフォーカス移動の解決方式

### 4.1 検討した方式

| 方式 | 概要 | 判定 |
|------|------|------|
| 空間的近傍（spatial navigation） | 各フォーカス可能ノードの画面上の矩形（x, y, w, h）を求め、方向キーが指す方向にある最近傍ノードへ移動する（Android TV 標準の `View.FOCUS_UP` 等に近い挙動） | **却下**（4.2 節） |
| **軸解決アルゴリズム** | `Node::List`/`Node::VirtualList` が持つ配置軸 `Axis`（縦/横/グリッド）を唯一の判断材料とし、4 方向すべてを「直近の祖先コンテナの `Axis` がその方向を扱うか」という単一の規則で解決する。`Axis` がその方向を扱わない場合だけでなく、扱っていても対象範囲内に候補が存在しない（境界到達）場合も祖先コンテナへエスケープし、no-op はエスケープの終端（トップレベルまで遡っても候補がない場合）のみで確定する（4.4 節） | **採用** |

### 4.2 採用理由・却下理由

軸解決アルゴリズムは次の制約をすべて満たす設計とする。

1. **4 方向すべてを同一規則（直近の祖先コンテナの `Axis`）で解決する対称設計**とする。非対称設計は
   `Axis::Grid` の行またぎ、`Axis::Horizontal` な棚内での `Up`/`Down` と `Left`/`Right` の重複を
   生むため避ける。
2. **エスケープ条件は「`Axis` がその方向を扱わない」場合と「扱うが範囲内に候補がない（境界到達）」場合の
   両方**とする。no-op はエスケープの終端のみで確定し、境界到達時の即時 no-op 確定は行わない（`Grid`・
   ネストしたリストの focus trap を防ぐ）。
3. `Axis::Grid` の `Left`/`Right` は行番号を変えない。行内に候補がない場合はエスケープとし、隣行への
   回り込みは行わない。
4. **性能契約**（4.5 節）: 移動 1 回の `item()` 呼び出しは連続する非フォーカス可能項目の run 長に比例し、
   最悪 O(コンテナ項目数) になる。`path` の深さで決まるのはエスケープの遡り段数のみである。
5. `rebuild` は `&mut self` 上の自己更新型 API とし、`current` と観測キャッシュを呼び出しをまたいで
   保持する。
6. 再解決は三段探索（観測キャッシュ照会 → 有界全域探索 → 先頭フォールバック）で行う。「構造は全域・
   中身は有界」とし、`List` は全展開、`VirtualList` は探索窓ヒント ± K に限定する（仮想化契約との両立）。
7. 探索窓ヒントを使うのは第 2 段のみとする。初回解決・第 3 段はヒント非依存の先頭スキャンとし、
   `FALLBACK_SCAN_LIMIT` により有界化する。上限内に候補がなければ `current = None` とする。
   `VIRTUAL_LIST_SEARCH_MARGIN`（第 2 段専用）とは別の定数である。
8. **reveal 契約**: `FocusRing` は `VisibleRange` を保持・変更しない。プラットフォームレイヤが path 上の
   すべての `VirtualList` 祖先を外側から順に最小移動で更新する。不変条件は「path 上の全 `VirtualList`
   セグメントの index が各 `VisibleRange` 内にあること」とする。

**却下理由**:

- 空間的近傍方式（4.1 節）は「実描画後の矩形」という共通コアが持たない情報（2 節「レイアウト情報の
  不在」）を要求し、`taffy` 統合が前提になるため却下する。`taffy` 統合（TASK-8.3-S4 相当、未着手）が
  完了し実描画後矩形を取得できるようになった時点で、`Axis` 宣言と実際の描画結果がずれるケース（例:
  折り返しレイアウトでコンテナの見た目が動的に変わる）への対応として再検討する価値がある。ただし
  v1 スコープでは `Axis` は開発者が明示的に宣言する契約であり、その宣言と実描画の整合はレンダラ実装
  （プラットフォームレイヤ）の責務とする（6.2 節）。
- `Left`/`Right` 無条件 no-op 案は、REQ-17 受け入れ基準 2・M6 完了基準が要求する左右のフォーカス移動を
  実現できないため採れない。Could という優先度は受け入れ基準の内容を変更しない。

**採用理由**:

- 共通コアにレイアウト情報を持ち込まない責務分界（`responsibility-boundary.md` 3 節）を維持したまま、
  「このコンテナは横一列に並ぶ」という**開発者が最初から知っている意味情報**を活用する。矩形計算・
  当たり判定は一切不要であり、空間的近傍方式とは異なる。
- **4 方向すべてが同一の規則に従う**（4.4 節）。3.2 節の path 機構を再利用して「直近の祖先コンテナの
  `Axis`」を読み取り、`Axis` がその方向を扱いかつ範囲内に候補がある場合はコンテナ内の隣接項目へ移動し、
  それ以外（扱わない場合・扱うが範囲内に候補がない場合の双方）は祖先コンテナへエスケープする。祖先
  コンテナを遡ってもトップレベル（暗黙の `Axis::Vertical`）まで候補が見つからない場合のみ no-op とする
  ——これは「情報がないから諦める」設計とは異なり、「縦一列という明示された配置には左右移動の対象が
  ない」という正しい意味論の帰結であり、`Up`/`Down` にも対称に適用される。
- Android TV の実際の UI パターン（横並びの「棚」を縦に並べる行グリッド型メニュー、`Axis::Horizontal` な
  `List`/`VirtualList` を `Axis::Vertical` な外側の並びに重ねる構成）にそのまま対応でき、REQ-17
  受け入れ基準 2 が要求する現実的な左右移動デモを TASK-17.2 で構築できる（9 節）。

### 4.3 型変更: `Axis` の追加（`Node::List` / `Node::VirtualList`）

`Node::List` / `Node::VirtualList` へ配置軸 `Axis` フィールドを追加する。

```rust
// node.rs に追加する型。既定値は Vertical（既存の縦一列前提の挙動を変えない安全側の既定）。
// 4 方向すべての解決規則を Axis バリアントごとに一意化する（4.4 節「軸解決アルゴリズム」）。
#[derive(Debug, Clone, Copy, PartialEq, Eq, Default)]
pub enum Axis {
    /// 子要素が縦一列に並ぶ（既定）。このコンテナ内では `Up`/`Down` が隣接項目へ移動し、
    /// `Left`/`Right` は祖先コンテナへエスケープする（4.4 節）。
    #[default]
    Vertical,
    /// 子要素が横一列に並ぶ。このコンテナ内では `Left`/`Right` が隣接項目へ移動し、
    /// `Up`/`Down` は祖先コンテナへエスケープする（4.4 節）。
    Horizontal,
    /// 子要素がグリッド状に並ぶ。`columns` は 1 行あたりの列数。`Left`/`Right` は
    /// `index / columns`（行番号）が変わらない範囲でのみ隣接 index へ移動し（行境界を
    /// 越えない）、`Up`/`Down` は `index ± columns` で行間を移動する。境界に達し自コンテナ内に
    /// 候補が無い場合は祖先コンテナへエスケープする（`Vertical`/`Horizontal` と同じエスケープ
    /// 条件）。`columns == 0` は `1` として扱う（panic を API 契約にしない、coding-rust.md の
    /// エラーハンドリング方針）。
    Grid { columns: usize },
}

// Node::List { expand, axis: Axis }
// Node::VirtualList { len, item, item_extent, axis: Axis }
```

`Screen` ビルダーは非破壊で拡張する。既存の `.list(expand)` / `.virtual_list(len, item, item_extent)` は
シグネチャを変更せず、内部で `axis: Axis::default()`（`Vertical`）を渡す。軸を明示したい呼び出し元は
新設する `.list_with_axis(expand, axis)` / `.virtual_list_with_axis(len, item, item_extent, axis)` を使う
（既存呼び出し元は無修正で動く、加法的設計・coding-rust.md 準拠）。

**移行コストの見積り**: 一方で `Node::List { .. }` / `Node::VirtualList { .. }` の直接構造体リテラル
（ビルダーを介さない構築）は `crates/fandhe-core` 内に計 42 箇所（`List` 21・`VirtualList` 21）存在し、
`axis` フィールド追加によりコンパイルエラーとして機械的に指摘される。3.1 節の `id` フィールド追加と
同様、TASK-17.2 の前提作業として計画する（8 節）。

### 4.4 フォーカス状態の型定義と移動アルゴリズム

フォーカス状態を保持する `FocusRing<S>`（設計上の名称。実装配置は 6 節参照）は以下の責務を持つ。
**性能上の理由（4.5 節）から、フォーカス可能ノードの path 列をツリー全体にわたって事前列挙・保持する
設計は採らない。** `FocusRing` が保持するのは「現在フォーカス中の 1 つの `FocusEntry`（path + id、
3.1 節で追加した安定識別子）」のみであり、移動先の解決は現在位置の近傍のみを都度辿ることで行う。

```rust
/// 現在フォーカス中のノードを「path + 安定識別子」の組で保持する（`label` ではなく
/// `WidgetId` を識別に用いる構成）。状態 `S` を所有せず、`Screen<S>` と `&S` を都度受け取って
/// 移動先を解決する（`Node::List::expand` 等の都度評価の設計を踏襲、render.rs と同じ思想）。
struct FocusEntry {
    /// フォーカス中ノードの path（3.2 節の探索順序上の位置）。「ツリー上の位置」を
    /// 指すだけで「論理的に同一の項目」を指し続ける保証はない（3.2 節）。
    path: Vec<usize>,
    /// `path` 解決時点で読み取ったノードの `WidgetId`（3.1 節）。`rebuild`（再解決時）・
    /// `activate_focus_at`（決定時、5 節）の双方で「今その path にある葉ノードは
    /// 本当に前回フォーカスしていた論理項目と同一か」を検証する一次情報として使う
    /// （「id による二層検証」参照）。
    id: super::widget::WidgetId,
}

struct FocusRing {
    /// 現在フォーカス中のノード。フォーカス可能ノードが 1 つも存在しない場合は `None`。
    current: Option<FocusEntry>,
    // observed: 「WidgetId → 最後に観測した path」の有界マップ（観測キャッシュ。使用時に
    // 必ず検証する verify-on-use 方式のため無効化管理を持たない。具体型・サイズ上限は
    // TASK-17.2 の裁量、本節「観測キャッシュと再捕捉保証の層別化」参照）
}

/// 4 方向とも「直近の祖先コンテナの `Axis` がこの方向を扱うか」で解決する
/// （本節「軸解決アルゴリズム」参照。`Up`/`Down` も `Left`/`Right` と対称に扱う）。
enum FocusDirection {
    Up,
    Down,
    Left,
    Right,
}
```

- **`id` による二層検証**: `FocusRing` は呼び出し元の自己申告に依存しない設計とする。汎用プラット
  フォーム層が任意の `on_click` による `S` の構造変化を常に把握できるという前提は成立しない（申告漏れは
  現実に起こり得る）。`FocusRing` は `path` を再解決するたびに、その path に現在存在するノードの
  `id`（3.1 節）を読み、`FocusEntry.id` と比較する。一致すれば同一の論理項目として採用し、**不一致で
  あれば構造変化を自動検知したとみなす**（下記「再解決アルゴリズム」）。決定操作（5 節）でも同じ `id`
  比較を最終防波堤として要求する。

- **再解決アルゴリズム（`rebuild`）**:

  ```rust
  impl FocusRing {
      /// 呼び出すたびに `self.current` を `id` 比較で自動検証し、必要なら復旧する自己更新型
      /// API（呼び出し元の構造変化申告に依存しない、上記「id による二層検証」）。`current` と
      /// `observed` は同一インスタンス上で呼び出しをまたいで引き継がれる（前回の `FocusEntry`
      /// を引数で渡し新しい `FocusRing` を返す再構築型シグネチャでは、呼び出しごとに `observed`
      /// （観測キャッシュ）が失われ第 1 段の照会が機能しないため、この自己更新型契約を採る）。
      /// `window_hints` は探索窓ヒント（コンテナごとの現在の `VisibleRange`）。呼び出しごとに
      /// 入力として受け取る読み取り専用の値であり、`FocusRing` は状態として保持しない
      /// （4.6 節の契約を維持）。具体型は TASK-17.2 の裁量。
      fn rebuild(
          &mut self,
          screen: &Screen<S>,
          state: &S,
          window_hints: /* コンテナ path → VisibleRange の読み取り専用ビュー */,
      ) {
          /* ... */
      }
  }
  ```

  1. `self.current` が `None`（画面表示直後の初回呼び出し）の場合は、ツリー先頭から最初のフォーカス
     可能ノードを探索し `current` とする（1 度きりのコスト、4.5 節。この走査の `VirtualList` の
     扱いは下記第 3 段と同じ「最初の一致で早期終了する走査」規則に従う）。
  2. `self.current` が `Some(entry)` の場合、`entry.path` にある現在のノードを 1 回だけ解決する
     （3.2 節の path 降下、`click_button_at` の既存降下ループと同じ反復実装を共通コア内部で共有する
     想定）。解決したノードが `Button`/`IndexedButton` で、かつその `id` が `entry.id` と一致すれば、
     `entry` をそのまま `current` に採用する（O(path の深さ) のみ、呼び出し元の申告なしで安全に
     継続できる主経路）。
  3. **id 不一致（または path が範囲外・非葉ノード）を検知した場合**（=構造変化を共通コアが自動検知した
     場合）、次の**三段探索**で同じ `id` を持つ葉ノードを探す。「構造は全域・中身は有界」の原則に基づく
     設計であり、ツリー全体を無条件に再列挙すると `VirtualList` の `0..len(state)` 全 index へ
     `item()` を呼ぶことになり仮想化契約（2 節）に反するため、構造（コンテナの骨格）と `VirtualList`
     の中身を分けて扱う。
     - **第 1 段（観測キャッシュ照会）**: 下記「観測キャッシュと再捕捉保証の層別化」のキャッシュに
       `entry.id` の目撃記録（最後に観測した path）があれば、その path を 1 回だけ解決して `id` 一致を
       検証する（verify-on-use）。一致すれば O(path の深さ) で `current` を確定する。記録が古く
       不一致なら記録を捨てて第 2 段へ進む（外れても正しさに影響しない、性能最適化に純化した段）。
     - **第 2 段（有界全域探索）**: `Node::expand_children` / `Screen::visit_expanded`（2 節）と同じ
       深さ優先・挿入順でツリーの**構造全体**を descend し、`Button`/`IndexedButton` の `id` を順に
       比較する。ただし `Node::List` は全展開する（仮想化契約を持たない経路、2 節・4.5 節）一方、
       `Node::VirtualList` の中身は**探索窓（呼び出し元が渡す探索窓ヒント ± マージン K 件、下記
       「観測キャッシュと再捕捉保証の層別化」の「探索窓ヒント」参照）**の index にのみ
       `item(state, index)` を呼ぶ（探索窓の有界化。K の具体値は本書では固定せず TASK-17.2 の
       実測で決定する、7 節）。これにより、フォーカス可能な子孫を持つコンテナ自体が
       親 `List` 内で並べ替え・挿入・階層変更された場合も確実に再捕捉でき、かつ `VirtualList` の
       全域列挙は発生しない。
     - **重複 `id` の扱い**: `WidgetId` の一意性は開発者が保証する契約（2 節・3.1 節、
       `Node::Widget` 系列の既存運用と同一）であり、イベント処理（`activate_focus_at`、5 節）とも
       一貫する前提である。この前提が破られ重複 `id` が存在する場合は、上記三段探索の探索順で最初に
       見つかった一致を採用すると規定する（探索順序の決定性を保証し、未定義動作にしない）。
     - **第 3 段（フォールバック）**: 第 2 段でも見つからない場合（項目自体が削除された場合、または
       `VirtualList` 内で探索窓の外へ移動した場合）のみ、ツリー先頭から最初のフォーカス可能ノードへ
       フォールバックする（初回 `rebuild` と同じ経路、上記 1. と同一）。この走査では探索窓ヒントを
       **用いず**（「先頭へのリセット」という意味論に合わせ、スクロール位置に依存しない決定的な
       着地点を保証する。ヒントがリスト中腹を指している場合に「先頭」が窓内の途中項目へずれることを
       防ぐ）、ツリー先頭から 3.2 節のツリー順で走査して**最初のフォーカス可能ノードで早期終了**する。
       `VirtualList` の中身は先頭（index 0）から順に評価し、候補が見つかった時点で停止する。この
       `item()` 呼び出し回数は「先頭に連続する非フォーカス可能項目の run 長 + 1」であり、方向キー
       移動時のスキップ探索とまったく同じ性能契約（4.5 節）に従う。**固定長の窓で打ち切らないため、
       フォーカス可能項目がリスト後方にのみ存在する画面でも必ず到達でき**、`current = None` になる
       のはツリー全体を走査し尽くしても候補が存在しない場合（契約どおり）のみである。窓外移動時の
       挙動が「再捕捉」ではなく「先頭リセット」になることは、下記「観測キャッシュと再捕捉保証の
       層別化」が定める仕様である。
  4. 呼び出し元が構造変化を申告する仕組み（`previous_focus = None` 強制のような設計）は**不要**
     とする。呼び出し元は「同一の `FocusRing` インスタンスを保持し、状態更新後に `rebuild` を呼ぶ」
     だけでよく（`current` と観測キャッシュはインスタンス内部で引き継がれる）、構造変化の検知・復旧は
     すべて `FocusRing` 内部で完結する（6.3 節の責務分界表を参照、6 節）。

#### 観測キャッシュと再捕捉保証の層別化

**観測キャッシュ（id→path の目撃記録）**: `FocusRing` は、自身の探索・解決（近傍探索・path 解決・
再解決）で `Button`/`IndexedButton` を評価するたびに、その副作用として「`WidgetId` → 最後に観測した
path」を有界サイズのマップへ記録する（プラットフォームレイヤの描画走査が観測結果を追記できる口を
設けてもよいが、契約上は `FocusRing` 内部の観測だけで成立する）。重要な性質は次の 3 点。

- **維持コストゼロ**: 記録はどのみち発生する項目評価への相乗りであり、キャッシュのために追加の
  `item()` 呼び出し・走査を一切行わない。なお、字義どおりの「挿入・削除のたびに索引を更新する」
  増分維持は、状態 `S` の変更を共通コアが観測できない本設計（`on_click: fn(&mut S)` の中身は
  不透明、上記「id による二層検証」の前提と同根）では更新のフック自体が存在せず成立しないため
  採らない。索引の正確な維持を試みるとツリーの再列挙が必要になり、解決すべき問題へ循環する。
- **verify-on-use（無効化管理の不要化）**: 記録は古くなり得るが、使用時に必ず path 再解決 + `id`
  比較で検証してから採用する（再解決アルゴリズム第 1 段）。外れた記録は捨てるだけで正しさに
  影響しないため、キャッシュ無効化の管理を一切必要としない（7 節の「逆引きキャッシュ」の見送り
  理由だった無効化の複雑さは、この方式では発生しない）。
- **有界メモリ**: マップはサイズ上限を持ち、超過時は古い記録から破棄する（上限値は TASK-17.2 の
  裁量）。破棄されても第 2 段以降が動くだけで、正しさに影響しない。

**探索窓ヒント（第 2 段の窓の基準点）**: `FocusRing` は
`VisibleRange`（スクロール位置・描画窓の起点）を状態として保持しない（4.6 節の契約）。
第 2 段が `VirtualList` の探索窓を定めるために必要な可視範囲の情報は、**呼び出し元（プラットフォームレイヤ）が `rebuild` の
引数として都度渡す読み取り専用の入力**（上記シグネチャの `window_hints`）とする。

- ヒントの所有・更新は引き続きプラットフォームレイヤの責務であり（4.6 節・6.2 節・6.3 節）、
  `FocusRing` は受け取った値をその呼び出しの中で読むだけで保持・変更しない。「状態として持たない」
  ことと「入力として受け取る」ことは矛盾しない（`state: &S` を都度受け取る既存の設計と同型）。
- ヒントを窓の基準に使うのは**第 2 段（再捕捉探索）のみ**である。初回解決と第 3 段（先頭
  フォールバック）の走査は「先頭へのリセット」という意味論に合わせ、ヒントに依らずツリー先頭から
  最初の一致で早期終了する走査を行う。固定窓では K 件を超える非フォーカス可能項目の先に実在する
  候補へ到達できないため、初回解決と第 3 段は早期終了走査とする（4.5 節「初回解決・リセットの
  コスト」）。有界窓 ± K が必要なのは第 2 段だけである——第 2 段は「存在しないかもしれない特定の
  `id`」を探すため打ち切り条件がなければ毎回全長を走査してしまうが、初回・第 3 段は「最初の候補」を
  探すため最初の一致で自然に停止し、コストは移動時スキップ探索と同じ契約（4.5 節）に収まる。第 2 段
  でヒントが提供されない `VirtualList` は先頭 K 件を既定の探索窓とする（探索の決定性を保証する
  既定値）。

**再捕捉保証の層別化**: `id` 不一致検知時にフォーカスを同一論理項目へ追随させる保証は、構造変化が
起きたコンテナの種別で次のように層別化する。これは「窓の外の項目は存在しないのと同じ」という仮想化の
設計思想（`list-virtualization-architecture.md`）をフォーカス復旧にも一貫して適用した帰結であり、
描画は窓外を実体化しないのに復旧だけが窓外まで責任を負うという契約の非対称を解消する。

| 構造変化の種類 | 再捕捉の保証 | 根拠 |
|------|------|------|
| `List` 内の並べ替え・挿入・削除、およびフォーカス可能な子孫を持つコンテナ自体の移動・階層変更 | **保証する** | 第 2 段が `List` を全展開する（仮想化契約の対象外、2 節） |
| `VirtualList` 内の移動で、移動先が探索窓（探索窓ヒント ± K 件）以内 | 保証する | 第 2 段が探索窓ヒント ± K 件の範囲で `item()` を評価する（上記「探索窓ヒント」）。なお項目が移動していない場合は第 1 段（`entry` 自身は前回 `current` 確定時の path 解決で観測済み）が O(path の深さ) で先に解決する |
| `VirtualList` 内の移動で、移動先が探索窓から K 件を超えて離れた位置 | **保証しない**（第 3 段の先頭フォールバック） | 仮想化契約により窓外は実体化しない。利用者に見えていない位置への移動であり、体感上も先頭リセットと区別がつかない |

#### 軸解決アルゴリズム（4 方向共通）

4 方向すべてを次の単一規則で解決する（対称設計、4.2 節参照）。

**コンテナと階層**: `current.path`（長さ `n`）の各セグメントは `List`/`VirtualList` を 1 段降下するごとに
1 つ追加される。したがって `t = n-1, n-2, ..., 1` はそれぞれ `path[..t]` が指すコンテナを表す。
**`t = 0`（path が空）は `Screen` の挿入順 `Vec<Node<S>>` を `Axis::Vertical` の暗黙コンテナとみなす**
（トップレベルとネストされたコンテナを同一規則で扱うための単純化。3.2 節「トップレベルは縦一列」という
既存の前提と矛盾しない）。

**コンテナ単位の解決表**（各コンテナが自身の `Axis` に応じて 4 方向のうちどれを自コンテナ内で解決し、
どれを祖先コンテナへエスケープするかを一意に定める）:

| `Axis` | `Up` | `Down` | `Left` | `Right` |
|--------|------|--------|--------|---------|
| `Vertical`（既定・トップレベル含む） | 隣接 index -1 | 隣接 index +1 | 祖先へエスケープ | 祖先へエスケープ |
| `Horizontal` | 祖先へエスケープ | 祖先へエスケープ | 隣接 index -1 | 隣接 index +1 |
| `Grid { columns }` | `index - columns` | `index + columns` | 同一行内 `index - 1` | 同一行内 `index + 1` |

**自コンテナ内で解決する場合**（`Vertical`/`Horizontal` の隣接 index 探索、`Up`/`Down`/`Left`/`Right` 共通）:

1. 隣接 index から開始し、フォーカス可能ノード（`Button`/`IndexedButton`）またはフォーカス可能な子孫を
   持つコンテナが見つかるまで同じ方向へ 1 つずつ進める（「連続する非フォーカス可能ノードをスキップする」
   規則、4.5 節）。
2. コンテナの項目数（`List::expand(state).len()` / `VirtualList::len(state)`）の範囲を超えても候補が
   見つからない場合（先頭・末尾で折り返さない）は、**下記「祖先コンテナへエスケープする場合」の手順へ
   進む**（「自コンテナがこの方向を扱う」ことと「移動先が実在すること」は別であり、後者が満たせない
   場合もエスケープ条件に含める。この結果 no-op が確定するのはエスケープの終端（トップレベルまで
   遡っても候補が無い場合）のみになる）。
3. 見つかった項目が `Button`/`IndexedButton` であればその `id` を読み取り新しい `FocusEntry` とする。
   ネストしたコンテナ（例: 棚の中にさらに棚がある構造）であれば、3.2 節のツリー順で辿った**最初の
   フォーカス可能ノード**へ descend する。

**`Axis::Grid { columns }` の解決**（`columns == 0` は `1` として扱う）:

- `Left`/`Right`: `index / columns`（行番号）が変わらない範囲でのみ `index ± 1` へ移動する。行番号が
  変わる場合（行末での `Right`・行頭での `Left`）は**行内に候補なしとして祖先コンテナへエスケープする**
  （「隣の行へ回り込まない」制約は維持する）。
- `Up`/`Down`: `index ∓ columns` へ移動する。範囲外（負・`len` 以上）なら祖先コンテナへエスケープする。
- 見つかった候補が非フォーカス可能ノードの場合、`Left`/`Right` は行番号一致条件を維持したまま同方向へ
  `± 1` ずつ、`Up`/`Down` は `± columns` ずつスキップを続ける。
- `Grid` は 4 方向すべてを自コンテナ内でまず解決を試みるが、境界に達し候補が尽きた場合は
  `Vertical`/`Horizontal` と同じ規則で祖先コンテナへエスケープする（斜め方向のショートカットは v1
  スコープ外、7 節）。

**祖先コンテナへエスケープする場合**（自コンテナの `Axis` がこの方向を扱わない場合、または扱うが対象
範囲内に候補が存在しない場合の両方が対象）:

1. `t` を 1 つ減らす（`path[..t-1]` が指すコンテナ、`t-1 == 0` ならトップレベル）。そのコンテナの `Axis`
   が同じ方向を扱え、かつ対象範囲内に候補が存在するか再判定する（上記「自コンテナ内で解決する場合」の
   規則をそのまま適用する）。
2. 候補が見つかる場合、**エスケープ元コンテナ自身の祖先コンテナ内での位置**（すなわち `path[t-1]`）を
   起点に、上記「自コンテナ内で解決する場合」の探索規則を適用する（`Grid` なら「`Axis::Grid` の解決」の
   規則）。
3. 見つかった項目がコンテナ（ネストした棚等）であれば、3.2 節のツリー順で辿った**最初のフォーカス可能
   ノード**へ descend する。**v1 の単純化**: エスケープ前に保持していた列位置（横方向のオフセット）は
   保持しない（列位置保持は 7 節「対象外」に記録する将来拡張）。
4. `t-1` のコンテナでも候補が見つからない場合、`t` をさらに 1 つ減らして 1.〜3. を繰り返す。`t == 0`
   （トップレベル、暗黙の `Axis::Vertical`）でも候補が見つからない場合は **no-op** で確定する
   （エスケープの終端。これが唯一の no-op 確定条件になる）。

この手順は `path` の長さ分だけ減衰しながら再帰するため必ず停止する。**表 + 探索規則 + エスケープ手順の
3 つで 4 方向 × 3 種の `Axis` × コンテナ境界をまたぐ場合の全組み合わせが一意に定まる**（下記「机上検証」
で実際のツリー例に適用して確認した）。

### 4.5 列挙・移動解決の性能契約（VirtualList 対応）

フォーカス可能ノードを `Vec<Vec<usize>>` として `0..len(state)` の全件で毎回列挙し
`FocusRing::rebuild` のたびに再実行する方式は、`VirtualList` の仮想化契約（2 節「VirtualList の
仮想化契約」）を実質的に迂回するため採用しない。本節は検討した方式と採用理由に加え、`id` 不一致時の
再解決探索（4.4 節、三段探索）の性能特性を記す。

- **却下した方式（全件事前列挙）**: `focusable_paths: Vec<Vec<usize>>` としてツリー全体のフォーカス
  可能ノードを毎回全列挙する方式。`VirtualList` を `0..len(state)` 全展開する必要があり性能契約に
  反する（2 節）。**却下**。
- **採用した方式（現在位置の近傍を遅延探索）**: `FocusRing` は「現在フォーカス中の `FocusEntry`
  （path + id）」のみを保持し、方向キー入力のたびに `current.path` を起点として、4.4 節「軸解決
  アルゴリズム」の**コンテナ単位の近傍探索**（自コンテナ内での隣接 index 探索、または祖先コンテナへの
  エスケープ）のみを行う。`Node::VirtualList` に到達した場合は `len(state)` で範囲境界のみを判定し、
  `item(state, index)` は実際に評価対象になった index に対してのみ呼び出す。**性能契約**: 移動 1 回
  あたりの `item()` 呼び出し回数は「連続する非フォーカス可能項目の run 長 + 1」に比例する。この
  run（4.4 節「連続する非フォーカス可能ノードをスキップする」規則が辿る区間）はコンテナの項目配置に
  依存し、**最悪ケース（コンテナ全体が非フォーカス可能項目で占められる場合）では O(コンテナの項目数)**
  になり得る。`path` の深さで上界が決まるのは**エスケープで遡る祖先コンテナの段数のみ**であり、
  スキップ探索自体の上界ではない。`id` はこの `item()` 呼び出しで得た `Node<S>` から読み取るだけで
  あり、追加の走査を発生させない。**採用**。
  - **実運用上の補足**: TV 向け `List`/`VirtualList` は原則としてフォーカス可能項目（`Button`/
    `IndexedButton`）の列であることを想定しており、見出し・区切り等の非フォーカス可能項目が挟まる
    場合もその run は短い定数長にとどまる想定である。この想定が崩れる大規模リスト（非フォーカス可能
    項目が長く連続する構成）への対策（フォーカス可能項目の索引化・スキップ探索の上限設定等）は、
    キャッシュ導入と同様に実測でボトルネックが確認された場合の再検討事項とし、v1 では導入しない
    （7 節「対象外」に記録）。
- **`id` 不一致時の三段探索コスト**: `rebuild` が `id` 不一致を検知した場合（4.4 節「再解決
  アルゴリズム」3.）のコストは段ごとに定まる。第 1 段（観測キャッシュ照会）は path 再解決 1 回 =
  O(path の深さ)。第 2 段（有界全域探索）は **O(`List` 項目の総数 + K × `VirtualList` の本数)**——
  `List` は全展開する（仮想化契約を持たない経路、2 節）が、`VirtualList` へは探索窓（探索窓ヒント
  ± K 件、4.4 節）にのみ `item(state, i)` を呼ぶため、リスト全長 `len` に比例する成分を持たない。
  **探索窓ヒントを窓の基準に使うのはこの第 2 段だけ**であり、第 3 段（先頭フォールバック）は窓を
  持たず、最初のフォーカス可能ノードで早期終了する走査を行う（コストは下記「初回解決・リセットの
  コスト」と同一、4.4 節第 3 段）。三段探索は
  「実際に構造変化が検知されたタイミング」にのみ発生し、変化のない方向キー連打では発生しない
  （共通コアが不一致を検知したときだけ動く設計であり、平常時（4.4 節の近傍探索が主経路の間）の
  コストは変わらない）。
  観測キャッシュの維持コストがゼロ（既存の項目評価への相乗りで、追加の `item()` 呼び出しを発生
  させない）であることは 4.4 節「観測キャッシュと再捕捉保証の層別化」を参照。
- **`Node::List`（非仮想化）の扱い**: `Node::List::expand` は仮想化契約を持たない設計であり
  （2 節）、`FocusRing` が `List` の子を辿る際に `expand(state)` を呼ぶことは既存の性能特性をそのまま
  引き継ぐだけである。
- **初回解決・リセットのコスト**: `self.current`
  が `None` の場合（画面表示直後の初回 `rebuild`）および第 3 段フォールバックは、ツリー先頭から最初の
  フォーカス可能ノードを見つけるまで走査し、最初の一致で早期終了する。この走査では探索窓ヒントを
  用いない（「先頭リセット」の着地点をスクロール位置に依存させないため）。
  `VirtualList` への `item()` 呼び出し回数は「先頭に連続する非フォーカス可能項目の run 長 + 1」に
  比例するが、`FocusRing` 実装は `VirtualList` 単位で走査件数の上限（実装定数 `FALLBACK_SCAN_LIMIT`）を
  設けており、**上限を超えて O(コンテナの項目数) に発散することはない**。上限内に候補が実在する限り
  必ず到達し、上限内に候補がない場合は `current = None`（フォーカス可能ノード不在時の既存契約と同じ
  扱い）に確定する（真に候補が存在しない場合との実装上の区別はしない。`move_focus`/`decide` はどちらも
  no-op になるだけで安全なため、REQ-17 の受け入れ基準上は問題にならない）。
- **選択理由（方式の比較）**: 「可視範囲と現在位置の近傍だけを遅延探索する」方式と「総件数と index を
  使って移動先を解決する」方式を比較検討した。後者は `List`/`VirtualList` が混在するツリー構造では
  結局各ノードの focusable 数を事前に把握する必要があり全展開が避けられない。近傍の遅延探索方式は
  `current` の path という局所情報のみから次の 1 手を解決でき、一般的なツリー構造に対しても追加の
  前提を必要としないため、こちらを採用する。

### 4.6 可視範囲の追随（reveal）契約

`FocusRing` はフォーカス移動の結果（新しい `FocusEntry`）を解決するのみで、`VirtualList` の描画窓
（2 節「VirtualList の仮想化契約」の `visit_windowed` が扱う可視 index 範囲、以下 `VisibleRange`）を
一切保持・変更しない（4.4・4.5 節）。このため、方向キー移動で `FocusRing::current` が現在の
`VisibleRange` の外側を指す状態が起こり得る（例: 大規模 `VirtualList` を数コマ先まで連続で移動した場合）。
本節はこの責務を契約として明文化する。

- **共通コア（`FocusRing`）側の責務**: 方向キー入力の解決結果として新しい `FocusEntry`（path）を返す
  ところまでに限定する。`VisibleRange`（スクロール位置・描画窓の起点）は保持せず、変更もしない
  （4.4・4.5 節の設計方針と一貫。共通コアにレイアウト・描画状態を持ち込まない責務分界、
  `responsibility-boundary.md` 3 節）。なお `rebuild` が再解決の**入力**として探索窓ヒントを呼び出し
  ごとに受け取ること（4.4 節「観測キャッシュと再捕捉保証の層別化」）は、状態として
  保持・更新しない本契約と矛盾しない（`state: &S` を都度受け取る既存設計と同型）。
- **プラットフォーム統合レイヤ（Android TV 描画側）の責務**: フォーカス確定後、**`FocusEntry.path`
  上に存在するすべての `VirtualList` 祖先**について対応する index（path の当該セグメント値）を求め、
  **外側から内側の順に**、各 `VirtualList` の `VisibleRange` にその index が入るよう描画窓の起点を
  **最小移動で**更新してから描画する（上方向へフォーカスが外れた場合は窓の先頭に、下方向へ外れた場合は
  窓の末尾に対象 index が入る位置へ揃える、一般的な scroll-into-view 相当の挙動）。`VirtualList` の
  項目が別の `VirtualList` を含むネスト構造では、内側の窓だけを更新しても外側の項目自体が窓外なら
  不変条件「focused path が `VisibleRange` 内」を満たせないため、reveal の対象を「path 上の全
  `VirtualList` 祖先」とし、外側から内側の順に各 `VisibleRange` を最小移動で更新する（外側の窓が
  確定しないと内側の項目が実体化されないため）。`Node::List` は仮想化契約を持たない（2 節）ため
  描画窓の概念自体がなく、この責務の対象外である（path 上に `List` と `VirtualList` が混在する場合は
  `VirtualList` のセグメントのみが reveal の対象になる）。
- **契約の形（不変条件）**: 「フォーカス確定 → 描画」の各フレームにおいて、**`focused path` 上の
  すべての `VirtualList` セグメントの index が、それぞれのコンテナの `VisibleRange` 内にあること**を
  描画側（プラットフォーム統合レイヤ）の不変条件とする（単一 `VirtualList` の場合は「`focused path` が
  `VisibleRange` 内にあること」と同義）。具体的な
  API 形状（`VirtualList` の描画窓起点の更新手段等）は本書では固定せず、実装タスク TASK-17.2 側の
  裁量とする（本書は責務と不変条件のみを設計対象とする、1 節のスコープ定義と一貫）。
- 6.3 節「分界の要約」表にこの責務分担を反映する（下記参照）。

## 5. 決定ボタン押下から既存イベントハンドリングへの接続経路

決定ボタン（Android TV リモコンの中央ボタン、`KeyEvent.KEYCODE_DPAD_CENTER` / `KEYCODE_ENTER` 相当）押下は、
`FocusRing::current`（`FocusEntry { path, id }`、4.4 節）を新設の id 版解決関数へ渡すことで、
**既存の path 降下ロジックを再利用しつつ、決定操作の整合性ガードを label から id へ置き換えて接続する**。

```rust
/// `click_button_at`（label 版、既存 API・非破壊で温存）と並置する id 版。
/// `path` 降下ロジックは共通の内部ヘルパー
/// （`resolve_node_at` 相当）へ抽出し、`click_button_at` と本関数の双方から
/// 呼び出す（重複実装を避ける）。
///
/// 解決した葉ノードの `id`（3.1 節で追加した `WidgetId`）が `id` 引数と一致する
/// 場合のみ `on_click` を発火する。不一致・path 範囲外・非葉ノードはいずれも
/// 状態を変更せず `false` を返す（`click_button_at` と同じエラーハンドリング方針、
/// coding-rust.md）。
pub fn activate_focus_at<S>(
    screen: &Screen<S>,
    path: &[usize],
    id: super::widget::WidgetId,
    state: &mut S,
) -> bool {
    /* ... */
}
```

```text
プラットフォームレイヤ（Android TV）
  └─ KeyEvent (KEYCODE_DPAD_CENTER) を受信
       │
       ▼
共通コア（fandhe-core::ui::event）
  ├─ FocusRing::current から FocusEntry { path, id } を取得
  └─ activate_focus_at(screen, &entry.path, entry.id, &mut state) を呼び出す
       │（Node::Button / Node::IndexedButton の on_click(state) が発火）
       │  id 不一致時は on_click を呼ばず false を返す（4.4 節「id による
       │  二層検証」の決定時検証、A08 対策）
       ▼
状態 S の更新（既存の状態管理契約、変更なし）
```

- `activate_focus_at` は葉ノードの `id` 一致を整合性ガードとして要求する。`FocusEntry` はこのガードへ
  そのまま渡せるよう、`current` 解決時（`rebuild`/`move_focus`）に対象ノードの `id` を併せて取得して
  保持する（4.4 節）。近傍探索（4.5 節）は対象ノード自体を 1 回評価するだけなので、`id` 取得のための
  追加コストは生じない。この `id` ガードは「フォーカス中とみなしていた項目が決定操作の瞬間には
  別の論理項目にすり替わっていないか」を最終確認する役割を持つ（4.4 節「id による二層検証」）。
  **`label` による旧ガードとの違い**: `label` は同一文字列を持つ別項目に対する誤発火が残存リスクと
  なり得るが、`WidgetId` は開発者がデータの永続的な同一性から採番する契約（3.1 節）のため、この
  残存リスクは解消される。
- **既存の `click_button_at`（label 版）は変更しない**（非破壊）。マウス・タッチ・エンタキー等、
  フォーカス状態を跨いで保持しない同期的なクリック処理（描画と同一フレーム内で完結する経路）は
  引き続き `click_button_at` を使える。`FocusRing` 経由の決定操作（複数フレームをまたいでフォーカス
  状態を保持する経路）のみ `activate_focus_at` を使う、という使い分けになる。
- **`Node::TextField` / `Node::Widget` は 3.1 節の定義によりそもそもフォーカス可能ノードの集合に
  含まれない**ため、決定ボタン → `activate_focus_at` の接続経路（本節）はこれらを扱う必要がない。
  `Widget<S>` トレイトへの決定ボタン発火契約の追加や `TextField` のフォーカス後入力配線は、3.1 節で
  述べた理由により後続タスクの検討事項とする（7 節「対象外」）。

## 6. ハイライト表示の表現方法と責務分界

### 6.1 共通コアが持つもの

- **「どの path が現在フォーカスされているか」という状態**（`FocusRing::current: Option<FocusEntry>`、
  4.4・5 節）。これは `Node<S>` の並び・`List`/`VirtualList` の展開結果という共通コアが既に把握している
  情報のみから導出できるため、プラットフォーム非依存に保てる。
- **方向キー入力 → 次にフォーカスすべき `FocusEntry` への解決ロジック**（4 節のアルゴリズム、4.5 節の
  性能契約）。矩形計算を含まないため、共通コアに置いても `responsibility-boundary.md` が定める
  「プラットフォーム固有コードを持ち込まない」制約に抵触しない。4 方向すべてが祖先コンテナの `Axis`
  宣言（4.3 節・4.4 節「軸解決アルゴリズム」）を読むだけであり、実描画ジオメトリを必要としない。
- **「このノードは現在フォーカスされているか」を問い合わせる読み取り API**
  （例: `FocusRing::is_focused(path: &[usize]) -> bool`）。プラットフォームレイヤの描画走査
  （`Screen::visit_expanded` / `render_headless` 相当の経路）がノードごとにこの API を呼び、
  ハイライト表示の要否を判定する。
- **構造変化の自動検知と復旧**（4.4 節「id による二層検証」）。
  `current` の `id` を path 再解決のたびに検証し、不一致を検知した場合は共通コア自身が
  三段探索（観測キャッシュ照会 → 有界全域探索 → 先頭フォールバック。4.4 節、仮想化契約と
  両立する設計）でフォーカスを復旧する。プラットフォームレイヤが構造変化を
  申告する契約は不要である（6.3 節の表を参照）。
- **決定操作の誤発火に対する最終防御**（`activate_focus_at` の id ガード、5 節・4.4 節「id による
  二層検証」）。`rebuild` 側の検証をすり抜けた場合でも、決定操作時に共通コア側のこのガードが
  誤発火を防ぐ最後の砦になる。
- **`VisibleRange`（描画窓）は保持しない**（4.6 節「可視範囲の追随（reveal）契約」）。
  `FocusRing` はフォーカス移動の解決結果（`FocusEntry`）を返すところまでが責務であり、`VirtualList` の
  スクロール位置・描画窓の起点は一切持たず変更もしない。`rebuild` の入力として探索窓ヒントを呼び出し
  ごとに受け取るが、これは読み取り専用の引数であり本責務分界を変えない。

### 6.2 プラットフォームレイヤ（Android TV 統合クレート）が持つもの

- **リモコンのキーイベント（`KEYCODE_DPAD_UP/DOWN/LEFT/RIGHT/CENTER`）を `FocusDirection` /
  決定操作へ変換する入力ブリッジ**。GameActivity 方式（`docs/architecture/android-activity-method.md`
  で確定済み）が配信する `KeyEvent` を、共通コアの `FocusDirection` enum へマッピングする層であり、
  Android 固有 API（`android.view.KeyEvent`）への依存はここに閉じ込める。
- **画面構築時に `Axis` を宣言する責務**（4.3 節）。横並びの棚・グリッドとして表示したい
  `List`/`VirtualList` には `.list_with_axis(expand, Axis::Horizontal)` 等を使う。これはプラットフォーム
  レイヤというより画面実装者（アプリ層）の責務だが、Android TV 向け画面を組む担当がこの層と重なる
  想定のため本節に記す。
- **同一の `FocusRing` インスタンスを保持し、状態更新後に `rebuild` を呼ぶ責務**（4.4 節）。構造変化の
  検知・復旧は共通コア内部で完結するため（6.1 節）、この層は「保持して呼ぶだけ」でよく、状態更新の
  意味を解釈する責務を負わない。あわせて、自身が管理する
  `VirtualList` の現在の `VisibleRange` を**探索窓ヒント**として `rebuild` へ渡す（4.4 節
  「観測キャッシュと再捕捉保証の層別化」。渡せない場合も先頭 K 件の既定窓で動作は成立するが、
  窓外フォールバックの発生範囲が広がるため、描画窓を持つ層としてヒントを渡すことを推奨する）。
- **ハイライトの実際の描画**（フォーカスリング・背景色変更・アウトライン等の具体的な視覚表現）。
  `Widget::paint` / `paint_styled` が返す `PaintCommand` 列に、`FocusRing::is_focused` の結果を
  加算的な装飾として反映する（`widget.rs` の既存コメント「`focused` は視覚状態と直交する
  （フォーカスリング等の加算的装飾）」という設計方針をそのまま踏襲）。ハイライトの具体的な色・太さ等の
  トークン解決は `docs/architecture/design-token-architecture.md` の枠組みに従う。
- **TV 型リモコン操作特有の UX 判断**（例: 決定ボタン長押しの扱い、戻るボタンとの関係）。REQ-17 の
  受け入れ基準は上下左右移動・決定ボタン選択の最小動作確認に限定されるため、これらは本書のスコープ外
  （7 節）。
- **可視範囲（`VisibleRange`）への追随（reveal / scroll-into-view）**（4.6 節）。フォーカス確定後、
  `FocusEntry.path` 上のすべての `VirtualList`
  祖先について、対応する index が各コンテナの `VisibleRange` に入るよう描画窓の起点を外側から内側の
  順に最小移動で更新してから描画する責務を負う。「`focused path` 上のすべての `VirtualList`
  セグメントの index がそれぞれの `VisibleRange` 内にあること」が各フレームの不変条件であり、
  具体的な API 形状は TASK-17.2 の裁量とする（4.6 節）。

### 6.3 分界の要約

| 責務 | 層 | 根拠 |
|------|-----|------|
| フォーカス可能ノードの列挙・順序決定 | 共通コア | レイアウト非依存、`Screen::visit_expanded` と同じ走査基盤で完結する |
| 方向キー → 次 `FocusEntry` の解決（4 方向とも `Axis` 宣言を参照する単一規則、4.4 節） | 共通コア | 軸解決アルゴリズム（4.4 節）はジオメトリ不要（4.2 節） |
| 決定ボタン → `activate_focus_at` 接続・id ガードによる誤発火防止（最終防御） | 共通コア | 既存の path 解決機構を再利用し、ガードを label から id へ置き換える（5 節・4.4 節） |
| `id` 不一致検知時の構造変化復旧（三段探索: 観測キャッシュ照会 → 有界全域探索 → 先頭フォールバック） | 共通コア | プラットフォームレイヤの申告に依存せず共通コアが自律的に検知・復旧する（4.4 節） |
| 画面構築時の `Axis` 宣言 | アプリ / プラットフォームレイヤ | コンテナの配置意図は画面実装者のみが知っている（4.3 節） |
| キーイベント（Android `KeyEvent`）の受信・変換 | プラットフォームレイヤ | Android 固有 API への依存を共通コアへ持ち込まない（`coding-rust.md`） |
| フォーカス確定後の `VisibleRange` への追随（reveal） | プラットフォームレイヤ | `FocusRing` はスクロール状態を持たない（4.6 節）。`VirtualList` の描画窓を扱うのは描画側の責務 |
| `rebuild` への探索窓ヒントの提供 | プラットフォームレイヤ | `VisibleRange` の所有・更新は描画側（4.6 節）。共通コアは呼び出しごとの読み取り専用入力として受け取るのみ（4.4 節） |
| ハイライトの実描画（色・アウトライン等） | プラットフォームレイヤ | 実描画バックエンド（`egui`/`eframe` 等、`responsibility-boundary.md` 2 節）の責務 |

## 7. 対象外（out-of-scope）

以下は REQ-17 の受け入れ基準・M6 完了基準に照らして本書の設計対象外と判断した。

- **`Node::TextField` のフォーカス対応**（3.1 節）: 決定ボタンではなくテキスト入力を受け付ける
  別種の操作契約であり、IME 合成（`docs/architecture/ime-architecture.md`）を含む入力配線は本書のスコープ
  （十字キー移動・決定ボタン選択の最小動作）とは別軸のため対象外とする。
- **`Node::Widget`（Action/Input カテゴリ）への決定ボタン配線**（3.1 節・5 節）: 現行 `Widget<S>`
  トレイト（`crates/fandhe-core/src/ui/widget.rs`）には Action/Input と Display/Container を判別する
  API がなく、カテゴリ判別 API・イベント発火契約の追加は共通コア全体のイベントディスパッチ基盤
  （`event.rs` 冒頭コメントが言及する未着手事項）と合わせて設計すべきであり、本書の対象外とする。
  TASK-17.2 の最小動作確認は `Node::Button`/`Node::IndexedButton` を用いた画面で行う前提とする。
- **空間的近傍（spatial navigation）方式**（4.1〜4.2 節）: `taffy` レイアウトエンジン統合（TASK-8.3-S4
  相当、未着手）が前提となるため対象外。
- **エスケープ時の列位置（横方向オフセット）保持**（4.4 節「軸解決アルゴリズム」手順 3.）: 棚から棚へ、
  または棚から `Grid` へ `Up`/`Down` でエスケープした際、v1 は常に移動先コンテナの**先頭**（3.2 節の
  ツリー順で最初のフォーカス可能ノード）へ着地し、エスケープ前の横方向位置（列）は保持しない。多くの
  TV リモコン UI が採用する「直前の列を記憶して同じ列へ着地する」挙動は、コンテナ間で列数・項目数が
  異なる場合の丸め規則の設計を要し、REQ-17 の最小動作確認には不要なため v1 では対象外とする。
- **`VirtualList` 内で探索窓の外へ移動した項目の再捕捉**: 構造変化で項目が
  探索窓（探索窓ヒント ± K 件、4.4 節）の外へ移動した場合、フォーカスは追随せず先頭フォールバックとなる（4.4 節
  「観測キャッシュと再捕捉保証の層別化」が定める仕様であり、欠陥ではない）。窓外まで再捕捉を保証
  するには全域列挙（仮想化契約違反）または永続的な索引の正確な維持（状態変更を観測できない本設計では
  成立しない、4.4 節）が必要であり、v1 では導入しない。実測・実利用で問題が確認された場合の再検討
  事項とする。
- **フォーカス可能項目の索引化・`move_focus` スキップ探索の上限設定**（4.5 節「採用した方式」）: 方向キー移動時（`move_focus`）が
  自コンテナ内で候補を探す近傍スキップ探索（4.4 節のスキップ規則）は、非フォーカス可能項目（見出し・
  区切り等）が長く連続するコンテナでは最悪 O(コンテナの項目数) になり得る。フォーカス可能項目のみを
  指す索引を `List`/`VirtualList` 側で事前に持たせる、またはこのスキップ探索自体に上限を設けて超過時は
  エスケープへフォールバックする等の対策で緩和できるが、TV 向け画面ではこの run が短い定数長にとどまる
  想定（4.5 節）であり、現時点で対策を要する実測結果がないため v1 では導入しない。実測でボトルネックが
  確認された場合の再検討事項とする。**対象外なのは `move_focus` のスキップ探索の上限のみであり、
  初回解決・第 3 段フォールバック**（`FocusRing` 自身が起点なしで行う先頭探索）は本項目とは別に
  `FALLBACK_SCAN_LIMIT` により有界化済みである（4.5 節「初回解決・リセットのコスト」。仮想化契約
  〔`item()` 呼び出しが `len` に比例しない〕を維持するための必須対応であり、実測次第で見送り可能な
  性能最適化である本項目〔`move_focus` のスキップ探索の上限〕とは性質が異なる）。
- **iOS/tvOS 等、Android TV 以外のリモコン操作対応**: REQ-17 は「Android TV フォーカス移動 UX 対応」に
  限定される（`04-requirements.md` L215）。tvOS は REQ-3（watchOS/visionOS の SwiftUI バインド）とは
  別軸であり、spec 上も明記されていないため対象外とする。

## 8. 後続タスク（TASK-17.2）で確認すべきこと

TASK-17.2（Android TV エミュレータでの最小動作確認、`05-tasks.md` L502〜507）は本書の設計方針を実装した
うえで、以下を実機（エミュレータ）で確認する。着手に先立ち、**前提となる型変更の機械的移行**
（`Node::Button`/`Node::IndexedButton` への `id: WidgetId` 追加・`Node::List`/`Node::VirtualList` への
`axis: Axis` 追加、3.1 節・4.3 節の移行コスト見積り参照）を完了させること。

1. **上下フォーカス移動**: 単一の
   `Axis::Vertical` な `List`（`Node::Button` を複数配置）を含む最小画面で、`KEYCODE_DPAD_UP`/`DOWN`
   により `FocusRing::current` がコンテナ内の隣接項目へ前後に移動し、ハイライト表示（6.2 節）が追随する
   ことを確認する。あわせて、`Axis::Horizontal` な棚を縦に 2 つ積んだ画面（4.4 節「机上検証」の構造）で
   `Down`/`Up` が棚の中を横に進まず、棚から出て次/前の棚の先頭項目へ移動する（=棚の中を横移動しない）
   ことを確認する。
2. **決定ボタン選択**: `KEYCODE_DPAD_CENTER`（または `KEYCODE_ENTER`）押下で、フォーカス中のボタンの
   `on_click` が発火し、状態 `S` が更新されることを確認する（5 節の接続経路の実地検証）。
3. **左右フォーカス移動の実移動確認**: `Axis::Horizontal` な `List`/`VirtualList`（横並びの「棚」を
   想定した最小画面、4.2 節「採用方式」参照）で `KEYCODE_DPAD_LEFT`/`RIGHT` により `FocusRing::current`
   がコンテナ内の隣接項目へ実際に移動し、棚の両端では折り返さず no-op になることを確認する（4.4 節
   「軸解決アルゴリズム」の検証、REQ-17 受け入れ基準 2 の直接的な検証ポイント）。あわせて
   `Axis::Vertical`（既定）なコンテナ・トップレベルの縦一列画面では `Left`/`Right` が
   `FocusRing::current` を変化させないことも確認する。
4. **`Axis::Grid` でのフォーカス移動**: `Axis::Grid
   { columns }` な画面（4.4 節「机上検証」の構造）で、`Left`/`Right` が行末・行頭で次/前の行へ越境しない
   こと（行境界の遵守）、`Up`/`Down` が `index ± columns` で行間を正しく移動すること、行の項目数が
   `columns` に満たない最終行（4.4 節の例では行 2 が 1 項目のみ）でも `Left`/`Right`/`Up`/`Down` が
   範囲外アクセスを起こさないことを確認する。あわせて、
   grid 最上行で `Up` を押した場合に祖先コンテナ（棚）へエスケープし、その先頭のフォーカス可能ノードへ
   移動すること（grid が focus trap にならないこと）、および grid 最終行で `Down` を押した場合に grid
   より下に候補が無ければ最終的に no-op になることを確認する。
5. **構造変化時のフォーカス復旧**: `List`/`VirtualList` の項目を削除・挿入・並べ替える状態更新の直後、
   **呼び出し元が何も申告しなくても** `rebuild` が `id` 不一致を自動検知し、同一 `id` を持つ論理項目へ
   フォーカスを追随させる（4.4 節「id による二層検証」）ことを確認する。項目自体が削除された場合は
   ツリー先頭へフォールバックすることも確認する。あわせて、
   **フォーカス可能な子孫を持つコンテナ自体が親 `List` 内で並べ替え・移動された場合**（例: 棚ごと順序が
   入れ替わる）でも、同一 `WidgetId` を持つ項目へ三段探索（4.4 節）で正しく再捕捉される
   ことを確認する。あわせて、`VirtualList` 内で項目が探索窓（探索窓ヒント
   ± K 件）の外へ移動した場合に、無応答にならず先頭フォールバック（4.4 節「観測キャッシュと再捕捉
   保証の層別化」が定める仕様）が動くこと、およびプラットフォームレイヤが `rebuild` へ探索窓ヒントを
   正しく渡せることも確認する。あわせて
   `activate_focus_at` の id ガード（5 節）により、万一 `rebuild` 側の復旧が誤った項目を指した場合でも
   誤った項目の `on_click` が発火しないことを確認する（決定操作の安全要件）。
6. **`GameActivity` 経由のキーイベント受信**: `docs/architecture/android-activity-method.md` が確定した
   GameActivity 方式で、Android TV エミュレータの D-pad 入力（物理リモコンのエミュレーション）が
   `KeyEvent` として正しく配信されるかを確認する（未検証の前提のため、本書の設計が成立するかの
   最初の検証ポイントになる）。
7. **フォーカス消失時の挙動**: フォーカス中のノードが状態変化で消える場合（4.4 節「id による二層検証」）
   の実装が、無応答（何も反応しないキー入力）を生まないことを確認する。あわせて、
   先頭に多数（K 件超）の見出し・区切りが連続する `VirtualList` を含む画面でも、
   初回 `rebuild`・第 3 段フォールバックの早期終了走査がリスト後方のフォーカス可能項目へ確実に到達し、
   画面がフォーカス不能にならないことを確認する。
8. **大規模 `VirtualList` でのフォーカス移動性能**: 数百〜数千項目規模の `VirtualList` を含む画面で、
   上下キー連打時に `item()` 呼び出しが近傍数件に留まり（4.5 節の性能契約）、全項目展開によるフレーム
   落ち・入力遅延が発生しないことを確認する。あわせて、項目の削除・挿入・コンテナ移動の直後に生じる
   `id` 不一致復旧（4.5 節「id 不一致時の三段探索コスト」）が体感できる遅延を
   生まないこと、および観測キャッシュのヒット時に復旧が O(path の深さ) で完了し `VirtualList` への
   `item()` 呼び出しが窓の範囲に留まることも確認する。
   さらに、**見出し・区切り等の非フォーカス可能項目を挟むリスト**でも
   キー入力遅延が体感上問題ないことを検証する。4.5 節が明記する最悪ケース（非フォーカス可能項目の run が
   長い場合に `item()` 呼び出しがコンテナの項目数に比例し得る）が TV 向け画面の実際の構成でボトルネック
   にならないことを実機で確認するのがこの項目の目的であり、想定外の遅延が確認された場合は 7 節に記録した
   索引化・スキップ上限設定の再検討を後続タスクとして起票する。
9. **可視範囲外への連続キー移動でのハイライト追随**:
   `VirtualList` で現在の `VisibleRange` の外側までフォーカスが連続移動した場合に、描画側が 4.6 節の
   reveal 契約（フォーカス確定後に描画窓の起点を最小移動で更新する不変条件）に従ってスクロールが自動的に
   追随し、ハイライトが常に画面内に表示されたまま操作が進むことを確認する。上方向へ外れた場合は窓の
   先頭に、下方向へ外れた場合は窓の末尾に対象が入ることも確認する。あわせて、
   `VirtualList` の項目が別の `VirtualList` を含むネスト構造で、外側・内側の両方の
   窓が更新されないと見えない位置へフォーカスが移動した場合に、path 上の全 `VirtualList` 祖先が
   外側から順に reveal され（4.6 節の不変条件）、ハイライトが表示されることを確認する。

上記の確認結果、特に 6（`GameActivity` のキーイベント配信可否）で想定外の制約が見つかった場合は、
6.2 節の入力ブリッジ設計（プラットフォームレイヤ側の責務）を見直す必要がある。
