## 2. 前提とするスキーマの最小要件

本節は本文書の解決アルゴリズムが S1（#157）のトークン型定義に対して要求する
最小要件を示す。実装の正は `crates/fandhe-core/src/token/schema.rs`（`TokenPath` /
`TokenValue`）であり、乖離があれば §7 の残課題として本文書を追補する。

想定する最小要件は以下のとおり。

- トークンキーはドット区切りの階層パス（例: `color.primary`、`spacing.md`）で
  表現され、Rust 側では文字列そのものではなく **パース済みの型**
  （`TokenPath` 相当、セグメント列を保持）として扱う。生の `String` を解決エンジンの
  境界を越えて受け渡さない（§5.1 のインジェクション対策と整合させるため）。
- トークン値は複数のカテゴリ（色・数値・文字列等）を持つ型付き列挙
  （`TokenValue` 相当）として表現され、解決エンジンはこの列挙のバリアントを
  跨いだ暗黙変換を行わない（§4.4 の型不一致エラーの根拠）。
- トークン定義の集合（トークンセット）はキー → 値またはキー → 参照のいずれかを
  持つマップとして表現される。

本文書の型シグネチャ案（§4）はこの想定に依存する箇所を「(S1 確定後に型名を
差し替える)」と明記し、想定と実際のスキーマが乖離した場合でも解決セマンティクス
自体（§3）は独立して成立するよう設計する。

## 3. 参照・エイリアスのモデル

### 3.1 参照構文の採用方針

W3C Design Tokens Community Group（DTCG）ドラフトが定める `{group.token}` 形式の
参照構文を、本設計の**外部シリアライズ表現（S17 が扱う JSON 等のファイル形式）に
限定して**採用する。Rust 内部の型（`TokenRef` 相当）では、この文字列構文を
パースした後の構造化データ（セグメント列を保持する `TokenPath` の別名または
newtype）として保持し、解決エンジンの内部処理・テスト・S19 の DSL 経由の参照は
一貫してこの構造化データ経由で行う。文字列パースは S17 が担う「外部定義ファイル
読み込み」の境界でのみ発生し、解決エンジン本体（S3）は生文字列を受け取らない。

**理由**: 生文字列を解決エンジンの奥まで持ち込むと、パス走査文字列（`../` 等）や
不正な文字集合の混入をエンジン内部の各所で再検証する必要が生じ、検証漏れの
リスクが増える（§5.1）。パースを境界の 1 箇所に集約し、それより内側は型で
不正な形式を排除する設計とする。

DTCG への準拠度（完全準拠か部分準拠か）は S17 の実装スコープであり、本文書は
「境界での構文検証後は構造化データを使う」という契約のみを確定させる。

### 3.2 参照文字列のパース契約（インジェクション対策の起点）

S17 が担うパース処理に対し、本設計は以下を契約として課す（実装は S17、検証観点は
S21 に引き継ぐ）。

- 許可文字集合: 英数字・`.`（階層区切り）・`-`・`_` のみ。それ以外の文字を含む
  参照文字列はパース段階で拒否し、`TokenError::InvalidReferenceSyntax` 相当の
  型付きエラーとする（§4.4）。
- パス長・セグメント数の上限を設ける（DoS 対策、§5.2 と同じ考え方を構文レベルにも
  適用する）。上限の具体値は S17 が実装時に決定し、本文書は「上限を設けること」を
  必須要件として明記するにとどめる。
- セグメント単体で `..` に一致するものは拒否する（パス走査対策。トークンキーの
  階層構造がファイルシステムパスではないため実害は限定的だが、将来の実装で
  トークンキーをファイルパス解決に流用しないという設計意図を明示する目的で
  契約化する）。

### 3.3 エイリアスチェーンの解決セマンティクスとテーマ適用順序

エイリアス（A → B → C のような多段参照）は次の段階を経て解決する。

1. **ベーストークン確定**: トークンセットに定義された生の値・参照を読み込む
   （S1 のスキーマに従う）。
2. **テーマ差分適用**（S4/S5・#160/#161 が設計・実装するテーマ切替機構との接続点）:
   アクティブテーマ（ライト/ダーク）が同一キーに対する上書き値・上書き参照を
   持つ場合、ベーストークンより優先する。本文書はこの優先順位（テーマ差分が
   ベースより優先される）のみを確定させ、テーマ切替のトリガー・データ構造自体は
   S4 のスコープとする。
3. **エイリアス解決**: 上記 2 段階を経て確定した「値または参照」の列に対し、
   参照であれば参照先を再帰的に辿り、最終的に値（非参照）へ到達するまで解決する。
   解決順序はテーマ適用**後**に行う。これは「テーマ差分がエイリアス先を差し替える
   ケース」（例: ライトテーマでは `button.background` が `{color.primary}` を、
   ダークテーマでは `{color.primary.dark}` を指す）を自然に表現するための順序であり、
   エイリアス解決を先に行うとテーマ差分がエイリアス済みの値に対して無力化される
   ため、この順序を必須の契約とする。

## 4. 解決エンジン API 案（S3 が実装する契約）

`fandhe-core` に新モジュール `token::resolver`（案）を追加し、以下の型・トレイトを
置く。型名は S1（#157）確定後に差し替え得る仮称とする。以下のコード片は
**シグネチャ案の提示のみ**を目的とし、メソッド本体は S3（#159）が実装する
プレースホルダである。`unimplemented!` はこの設計文書の時点では未実装であることを
示す仮の記法にすぎず、実装コードとして `unimplemented!` や `unwrap()`/`expect()` を
残してよいという意味ではない。§4.1 で定めるとおり、S3 が実装する本体は
未定義・循環参照・型不一致等のいずれの場合も panic せず `Result` で返さなければ
ならない（coding-rust.md の panic 禁止方針）。

```rust
/// トークン間の参照・エイリアスを解決するエンジン（TASK-8.4-S2 設計、S3 実装）。
///
/// 構築時にトークンセットとアクティブテーマを受け取り、`resolve` で
/// 個別のトークン参照を最終値まで解決する。解決結果は内部でキャッシュし、
/// テーマ切替（S4/S5）時に無効化される（§4.3）。
/// 二層アーキテクチャ（REQ-2）上は共通コアに閉じ、描画バックエンド等の
/// プラットフォーム固有クレートには依存しない。
pub struct TokenResolver {
    // トークンセット・アクティブテーマ・解決結果キャッシュを保持する
    // （具体的なフィールド構成は S1 のスキーマ確定後に S3 が決定する）。
}

impl TokenResolver {
    /// トークンセットとアクティブテーマから解決エンジンを構築する。
    ///
    /// S19（AI 型安全 DSL からのトークン参照 API）はこの構築を
    /// アプリ起動時・テーマ切替時に呼び出す想定。
    pub fn new(/* tokens: TokenSet, theme: ThemeId */) -> Self {
        unimplemented!("S3（#159）が実装する")
    }

    /// 単一のトークン参照を最終値まで解決する。
    ///
    /// 呼び出し元（S19 の DSL 参照 API・S2 が設計する各種ウィジェット
    /// スタイル適用箇所）は、この戻り値の `Result` を必ず処理し、
    /// エラー時に panic しない（coding-rust.md の panic 禁止方針に従う）。
    pub fn resolve(&self, _reference: &TokenRef) -> Result<ResolvedValue, TokenError> {
        unimplemented!("S3（#159）が実装する")
    }

    /// トークンセット全体を起動時・テーマ切替時に一括解決し、内部キャッシュへ
    /// 反映する。個別の `resolve` 呼び出しはこのキャッシュを参照する
    /// （§4.3 のキャッシュ戦略）。
    pub fn resolve_all(&mut self) -> Result<(), Vec<TokenError>> {
        unimplemented!("S3（#159）が実装する")
    }
}

/// パース済みのトークン参照（§3.1）。生文字列は境界（S17）でのみ扱い、
/// これより内側は本型を介して受け渡す。
pub struct TokenRef {
    // セグメント列（例: ["color", "primary"]）を保持する。
}

/// 解決済みの最終値。トークンのカテゴリ（色・数値等）を跨いだ暗黙変換を
/// 行わないため、`TokenValue`（S1 のスキーマ）のバリアントをそのまま保持する。
pub struct ResolvedValue {
    // S1 の TokenValue 型を保持する（型名は S1 確定後に差し替え）。
}
```

### 4.1 未解決トークンのフォールバック方針

`resolve` は未定義・循環参照・型不一致等いずれの場合も **panic せず `Result` で
返す**（coding-rust.md の「panic を API 契約にしない」方針に従う）。呼び出し元
（S19 の DSL 参照 API・ウィジェットスタイル適用箇所）がエラー時にどう振る舞うか
（既定値へフォールバックする・画面描画を中断する等）は、本設計のスコープ外とし、
呼び出し元（S19・TASK-8.3 系のスタイル適用箇所）が個別に決定する。解決エンジン
自体は「フォールバック値を勝手に補って返す」ことをしない（呼び出し元が
エラーを握りつぶしたのか気付かないまま不正な見た目で動作し続けるリスクを避ける
ため）。

### 4.2 型付きエラー（4 分類）

`thiserror` を用いた型付きエラー（coding-rust.md 準拠、`unwrap()`/`expect()` を
実装コードで使わない）とし、以下の 4 分類を必須とする。S18（#174、バリデーション・
エラー報告）はこの分類をそのまま集約・報告の単位として引き継ぐ。

```rust
/// トークン解決時のエラー分類（TASK-8.4-S2 設計、S3 実装）。
///
/// S18（バリデーション・エラー報告）はこの分類を集約し、開発者・AI 双方に
/// 解釈しやすい形（REQ-13 のコンパイルエラー解釈容易性の思想を実行時
/// エラーメッセージにも適用する）で報告する。
#[derive(Debug, thiserror::Error)]
pub enum TokenError {
    /// 参照先のトークンキーがトークンセットに存在しない。
    #[error("未定義のトークン参照です: {reference}")]
    UndefinedReference { reference: String },

    /// 参照元と参照先でトークンのカテゴリが一致しない
    /// （例: 色トークンがスペーシングトークンを参照している）。
    #[error("トークンの型が一致しません: {reference} は {expected} を期待しましたが {actual} でした")]
    TypeMismatch {
        reference: String,
        expected: &'static str,
        actual: &'static str,
    },

    /// エイリアスチェーンが循環している（§5.2 の検出アルゴリズムで検知）。
    #[error("循環参照を検出しました: {chain}")]
    CircularReference { chain: String },

    /// エイリアスチェーンの深さが上限を超えた（DoS 対策、§5.2）。
    #[error("エイリアスチェーンの深さが上限（{limit}）を超えました: {reference}")]
    MaxDepthExceeded { reference: String, limit: u32 },
}
```

### 4.3 解決結果のキャッシュ戦略とテーマ切替時の無効化

- `resolve_all` による一括解決結果を `TokenResolver` 内部にキャッシュし、
  個別の `resolve` 呼び出しは可能な限りこのキャッシュを参照する（エイリアス
  チェーンを毎回再帰的に辿るコストを避けるため）。
- アクティブテーマが切り替わった場合（S4/S5 が担うテーマ切替機構からの通知）、
  キャッシュ全体を無効化し `resolve_all` を再実行する契約とする。部分無効化
  （変更のあったキーのみ再計算する差分更新）は本設計のスコープ外とし、
  §7 の残課題とする（S3 実装時の初期実装は全件再計算で構わない）。
- キャッシュの具体的なデータ構造（`HashMap` 等）は S3 の実装詳細とし、本文書は
  「全件無効化・再計算」という契約のみを確定させる。

## 5. 境界条件・安全設計

### 5.1 参照文字列のインジェクション対策（OWASP A03）

§3.2 で定めた許可文字集合・パス長上限によるパース時検証に加え、解決エンジン
本体（`TokenRef` を受け取った後の処理）は以下を前提とする。

- `TokenRef` はパース済みの構造化データであり、解決エンジンがこれを任意の
  シェルコマンド・ファイルパス・クエリへ文字列展開することは一切ない
  （トークン解決はメモリ上のマップ検索のみで完結する）。
- 外部定義ファイル（S17）から読み込んだトークン定義値そのもの（色コード・
  数値等）についても、解決エンジンはこれらを検証済みの `TokenValue`
  （S1・S18 が検証を担う）としてのみ受け取り、生の文字列としては扱わない。

### 5.2 循環参照の検出と最大解決深さ

- **検出アルゴリズム**: エイリアスチェーンを辿る際、訪問済みの `TokenRef`
  集合（`HashSet` 相当）を保持し、既に訪問済みのキーへ再度到達した時点で
  `TokenError::CircularReference` を返す（DFS 中の visited set 方式）。
- **最大解決深さ**: 循環していない場合でも、悪意ある・誤ったトークン定義に
  よる異常に深いエイリアスチェーンがスタックオーバーフロー・過大な計算時間を
  引き起こさないよう、最大解決深さの上限を設ける（DoS 対策、OWASP A05）。
  上限の具体値は S3 実装時に決定するが、通常のデザイントークン運用
  （2〜3 段のエイリアスが一般的）を大きく超える値（例: 数十段）を初期値とし、
  設定可能にするかは S3 のスコープとする。上限を超えた場合は
  `TokenError::MaxDepthExceeded` を返し、panic・無限ループのいずれも
  発生させない。
- 循環検出・深さ上限のいずれも、解決処理を**再帰関数ではなく明示的なスタック
  （ループ）で実装する**ことを推奨する（Rust の再帰はスタックオーバーフロー時に
  `Result` を返せず即座に abort するため、上限チェックを関数呼び出しの外側で
  行える明示的ループの方が「panic しない」契約と整合する）。この実装方針の
  採否は S3 が決定する。

### 5.3 外部定義ファイル（S17）から渡される信頼できない入力への前提条件

- 解決エンジンは、S17 が読み込んだトークン定義がスキーマ検証済み
  （S18 のバリデーションを経た後）であることを前提とし、生のデシリアライズ
  結果を直接受け取らない。S17 → S18（検証）→ 解決エンジンという順序を
  データフローの契約とする。
- 上記前提が崩れる経路（S18 を経ずに外部ファイルを直接解決エンジンへ渡す実装）
  が将来追加された場合は、本設計の §5.1・§5.2 の対策が効かなくなるため、
  S3 実装時・以降の変更時にこのデータフロー契約を維持することをレビュー観点
  として明記する。

### S21 が対象とすべきテスト観点（最小限）

1. **正常解決**: 参照を持たない直接値の解決、1 段エイリアスの解決。
2. **多段エイリアスチェーン**: 2〜3 段の参照を経て最終値に到達するケース。
3. **テーマ差分との組み合わせ**: ライト/ダークでエイリアス先が異なるケース
   （§3.3 の順序契約が正しく機能することの確認）。
4. **循環参照**: 自己参照（A → A）・間接循環（A → B → A）の両方で
   `TokenError::CircularReference` が返ること（panic しないこと）。
5. **未定義参照**: 存在しないキーへの参照で `TokenError::UndefinedReference` が
   返ること。
6. **型不一致**: 色トークンがスペーシングトークンを参照する等のケースで
   `TokenError::TypeMismatch` が返ること。
7. **最大深さ超過**: 上限を超えるチェーンで `TokenError::MaxDepthExceeded` が
   返り、スタックオーバーフロー・ハングが発生しないこと。
8. **不正な参照構文**（S17 のパース境界のテストとの重複を許容）: 許可文字集合
   外の文字を含む参照文字列が拒否されること。

## 7. 残課題

- **§2 と実装型の照合**: §2 の最小要件を `schema.rs` の `TokenPath` / `TokenValue`
  の定義と照合し、乖離があれば本文書を追補する。
- **DTCG 互換性の程度**: 完全準拠か部分準拠（`{group.token}` 構文のみ採用し、
  DTCG の型システム・拡張仕様は採用しない等）かは S17 が実装時に最終決定する。
  本文書は構文レベルの採用のみを確定させた。
- **キャッシュの部分無効化**: §4.3 で述べたとおり、テーマ切替時の差分更新
  （変更キーのみ再計算）は本設計のスコープ外とした。画面数・トークン数が
  増えた場合の性能への影響は、S3 実装後の実測を踏まえて S5 または後続の
  最適化 sub-issue で検討する（out-of-scope-tracking.md に従い、性能上の
  課題が顕在化した時点でユーザー確認のうえ Issue 化を検討する）。
- **最大解決深さの具体値**: §5.2 で「数十段程度」とした上限の具体値・
  設定可能性の要否は S3 実装時に決定する。
