## 2. テーマモデル

### 2.1 `ThemeVariant`（ライト/ダークの閉じた列挙）

```rust
/// アクティブテーマの区分（ライト/ダークの閉じた列挙、TASK-8.4-S4 設計）。
///
/// S2（`token-resolution-architecture.md` §4）が `TokenResolver::new` の
/// シグネチャ案で仮称としていた `ThemeId` に対応する型であり、本文書が
/// 正式名称を `ThemeVariant` として確定する。以降 `ThemeId` という名称は
/// 使わない（S3/S5 実装時の混同を避けるため、本節が SSOT）。
///
/// 初期実装はライト/ダークの 2 値に限定し、カスタムテーマ（3 値目以降の
/// バリアント追加）は §7 の未解決事項とする（拡張時は非網羅的 match を
/// 強制しないよう `#[non_exhaustive]` の付与可否を含めて S5 が判断する）。
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum ThemeVariant {
    Light,
    Dark,
}
```

### 2.2 `Theme`（S1 プレースホルダの確定）

`Theme` は「ベース `TokenSet` に対するテーマ差分オーバーレイ」を表す型とし、
テーマそのものが独立した全トークン集合を持つわけではない。

```rust
/// ライト/ダーク 1 テーマ分のトークン差分（TASK-8.4-S1 §5.2 のプレースホルダを
/// 本文書が確定する）。
///
/// ベース `TokenSet`（S1 §5.2）に対する「同一キーへの上書き値・上書き参照」の
/// 集合として表現する。差分にキーが存在しない場合はベース値を使う
/// （§2.3 のフォールバック意味論、S2 §3.3 の優先順位契約と整合）。
/// ダークテーマがベースの全キーを再定義することを強制しない設計とする。
///
/// 配置は S1 §5.1 のモジュール配置案どおり `crates/fandhe-core/src/tokens/
/// theme.rs`（実ファイル分割は S5 の実装判断に委ねる、S1 §5.1 の留保を継承）。
pub struct Theme {
    variant: ThemeVariant,
    // キー → 上書き値/上書き参照 のマッピング（S1 の TokenKey / TokenValue を
    // 使う、フィールド構成は S1 の実際の型確定後に S5 が決定する）。
}
```

**用語 SSOT（型名の対応表、S3/S5 が別名を発明しないための一覧）**:

| 本文書での名称 | 役割 | S1/S2 側の対応 |
|---------------|------|----------------|
| `ThemeVariant` | ライト/ダークの区分（列挙） | S2 §4 の仮称 `ThemeId` を置換する正式名称 |
| `Theme` | 1 テーマ分のトークン差分（オーバーレイ） | S1 §5.2 の `Theme` プレースホルダの確定形 |
| `ThemePreference` | ユーザー/OS 設定の 3 値（§2.4） | 新設（S1/S2 に対応なし） |

モジュール配置は S1 §5.1 の `crates/fandhe-core/src/tokens/`（複数形）を正とする。
S2 §4 のコード例に登場する `token::resolver`（単数形）は S2 文書中の仮称であり、
本文書は `tokens::resolver`（S1 の配置案に合わせた複数形）を採用することを
明記する。この乖離は S2 §7 の残課題と同様、S3 実装時に解消されるべき事項として
本文書でも改めて記録する。

### 2.3 フォールバック意味論

`Theme` の差分にキーが存在しない場合、解決エンジン（S2/S3）はベース `TokenSet`
の値を使う。この意味論は S2 §3.3 の「テーマ差分がベースより優先されるが、
テーマ適用は差分が定義するキーにのみ及ぶ」という前提と一致し、本文書はこれを
`Theme` 型の契約として明記する（新規カテゴリ・トークンを追加した場合に、
既存のダークテーマ定義を全件更新する必要がない設計とする）。

### 2.4 `ThemePreference`（3 値モデル）とプラットフォーム境界

```rust
/// ユーザー/OS のテーマ設定意図（TASK-8.4-S4 設計）。
///
/// `System` は「OS のライト/ダーク設定に追従する」という**意図**を表すのみで、
/// OS 設定の実際の値（現在ライトかダークか）はコアが直接検出しない
/// （REQ-2 の依存方向: 最適化レイヤ → コアの一方向。コアが OS API・環境変数を
/// 読むと `.claude/rules/security.md` の A05「過剰な権限・依存」に抵触する）。
///
/// 契約: `ThemePreference::System` が設定されている場合、OS のライト/ダーク
/// 判定はプラットフォーム統合レイヤの責務とし、判定結果を `ThemeVariant`
/// （具体値）としてコアの切替 API（§3.2）へ渡す。コアが公開する状態は常に
/// 「現在解決済みの `ThemeVariant`」であり、`ThemePreference` 自体は
/// プラットフォームレイヤから見た「なぜこの `ThemeVariant` になったか」の
/// 入力パラメータという位置づけに限定する（コア内部で `System` のまま
/// 保持し続けて解決を先延ばしにする設計にはしない。§3.2 のシグネチャ参照）。
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum ThemePreference {
    System,
    Light,
    Dark,
}
```

## 3. アクティブテーマ管理と切替 API

### 3.1 所有者: `TokenResolver`

S2 §4 は既に `TokenResolver` が「トークンセット・アクティブテーマ・解決結果
キャッシュを保持する」と確定させている。本文書はこれを踏襲し、**アクティブ
テーマの可変状態は `TokenResolver` が単独で所有する**設計とし、別途
「テーママネージャ」のような並行の所有者を新設しない（S2 §4.3 のキャッシュ
無効化契約と単一の所有者でなければ整合が取れないため）。

```rust
impl TokenResolver {
    /// 現在のアクティブテーマ区分を返す。
    pub fn active_theme(&self) -> ThemeVariant {
        unimplemented!("S5（#161）が実装する")
    }

    /// アクティブテーマを切り替える。
    ///
    /// 切替の効果（S2 §4.3 契約の遵守、§4 参照）:
    /// 1. 保持するアクティブテーマを `variant` へ更新する
    /// 2. 解決結果キャッシュを全件無効化する
    /// 3. `resolve_all` を再実行する
    ///
    /// `variant` が現在のアクティブテーマと同一の場合は何もせず即座に返す
    /// （§4.2 の冪等契約、高頻度切替による無駄な再計算を避ける DoS 対策）。
    /// クロージャを引数に取らない（REQ-13 整合）。
    pub fn set_active_theme(&mut self, variant: ThemeVariant) -> Result<(), Vec<TokenError>> {
        unimplemented!("S5（#161）が実装する")
    }
}
```

`TokenResolver::new`（S2 §4）のシグネチャ案 `new(tokens: TokenSet, theme:
ThemeId)` は、本文書の型名確定（§2.2 の対応表）に伴い
`new(tokens: TokenSet, initial_theme: ThemeVariant)` と読み替える。

### 3.2 テーマ世代カウンタ（`StateStore::version` とは別系統）

`state/store.rs` の `StateStore<S>::version`（`u64` カウンタ、状態更新のたびに
増加）は、プラットフォーム統合レイヤが**アプリ状態 `S` の再描画要否**を判定する
ためのフックである。テーマ切替はアプリ状態 `S` の変更ではなく（`widget.rs`
冒頭のコメントが明記するとおり、ウィジェット/視覚状態はアプリ状態 `S` に
含めない設計方針と同様、テーマもアプリ状態ではない）、両者を混同しない。

したがって、テーマ切替の再描画通知には `StateStore::version` と同型だが
**独立したカウンタ**（以下「テーマ世代」）を、`TokenResolver` 自身が保持する
設計案を示す（具体的なフィールド追加・配線は S5 のスコープ）。

```rust
impl TokenResolver {
    /// テーマが切り替わるたびに増加する世代カウンタ。
    ///
    /// `StateStore::version`（アプリ状態の変更検知、`state/store.rs`）とは
    /// 独立したカウンタである。プラットフォーム統合レイヤは両方を監視し、
    /// いずれかが変化したら再描画する想定（具体的な監視方法は S5/プラットフォーム
    /// レイヤの実装詳細）。
    pub fn theme_generation(&self) -> u64 {
        unimplemented!("S5（#161）が実装する")
    }
}
```

同一テーマへの再切替（§3.1 の冪等契約）では `theme_generation` を進めない。

### 3.3 プラットフォームレイヤからの利用パターン

- 明示切替（アプリコードが `ThemeVariant::Dark` 等を直接指定）: DSL 経由の
  公開 API（S19、#175）が内部で `TokenResolver::set_active_theme` を呼ぶ
- OS 設定変更の通知: プラットフォームレイヤが OS のライト/ダーク変更通知
  （具体 API は S16/プラットフォームレイヤの実装詳細、本文書は関与しない）を
  受け、解決済みの `ThemeVariant` を `set_active_theme` へ渡す
- 起動時の初期テーマ決定: `ThemePreference`（§2.4）に応じてプラットフォーム
  レイヤが初期 `ThemeVariant` を決定し、`TokenResolver::new` の
  `initial_theme` へ渡す

いずれの経路も、コアが公開する API はクロージャを取らない `ThemeVariant` 値
渡しの関数呼び出しに限定され（REQ-13 整合）、OS API・環境変数の直接参照は
コア側に一切持ち込まない（REQ-2 の一方向依存を維持）。

## 4. 切替トリガーと伝搬フロー

### 4.1 トリガー 3 種

| トリガー | 発生元 | コアへの入力 |
|---------|--------|--------------|
| (a) アプリコードによる明示切替 | S19 の DSL 参照 API | `ThemeVariant`（直接指定） |
| (b) OS 設定変更のプラットフォームレイヤ経由通知 | プラットフォームレイヤ | `ThemeVariant`（OS 判定結果を解決済みで渡す、§2.4） |
| (c) 起動時の初期テーマ決定 | プラットフォームレイヤ or アプリコード | `ThemeVariant`（`ThemePreference` から解決済み） |

### 4.2 切替時の処理契約（冪等性を含む）

1. `set_active_theme(variant)` 呼び出し
2. `variant` が現在のアクティブテーマと同一 → 何もせず正常終了（冪等、
   OWASP A04 対策として §5 で詳述する高頻度切替時の DoS 緩和を兼ねる）
3. 異なる場合: アクティブテーマ更新 → 解決結果キャッシュ全件無効化
   → `resolve_all` 再実行（S2 §4.3 契約） → `theme_generation` を +1
4. 呼び出し元（S19 の DSL 参照 API・プラットフォームレイヤ）が
   `theme_generation`（またはプラットフォーム固有の再描画トリガー）を見て
   全画面再描画を要求する

`resolve_all` は S2 §4.1 の方針同様、エラー時も panic せず
`Result<(), Vec<TokenError>>` で返す（coding-rust.md の panic 禁止方針）。

### 4.3 部分無効化はスコープ外

S2 §4.3・§7 が既に「部分無効化（変更キーのみ再計算する差分更新）は設計の
スコープ外」としており、本文書もこれを踏襲する。テーマ切替時は常に全件
再解決とし、性能上の課題が顕在化した場合は out-of-scope-tracking.md に従い
別途 Issue 化を検討する（§7）。

### 3.4 外部テーマ定義のデータフロー契約

S2 §5.3 が確立した「S17（読み込み）→ S18（検証）→ 解決エンジン」という
データフロー契約を、テーマ差分（`Theme`）にも同様に適用する。外部ファイルから
読み込んだテーマ差分は S18 の検証を経ずに `TokenResolver`（テーマ差分として）
へ渡してはならない。この契約が崩れる経路が将来追加された場合、S2 §5.1・§5.2
の対策（インジェクション対策・循環検出）がテーマ差分側では効かなくなるため、
S5・S17 実装時のレビュー観点として明記する（OWASP A08 対応、§8 参照）。

## 6. S22（#178）が対象とすべきテスト観点

1. **ライト→ダーク切替で解決値が変わること**: 差分で上書きされたキーが、
   切替後に `resolve` すると新しい値を返すこと
2. **差分未定義キーのベースフォールバック**: ダークテーマの差分に存在しない
   キーが、切替後もベース値を返すこと（§2.3）
3. **切替後のキャッシュ無効化**: 切替前にキャッシュされた解決結果が、切替後は
   再計算されること。S2 §3.3 の「エイリアス先差し替えケース」（ライト/ダーク
   で参照先自体が異なるエイリアス）を含む
4. **同一テーマへの再切替が冪等であること**: 同じ `ThemeVariant` を連続して
   渡しても `theme_generation` が進まず、`resolve_all` が再実行されないこと
   （§4.2 の冪等契約、パフォーマンス観点も含む）
5. **`ThemePreference::System` の伝搬**: プラットフォームレイヤが解決した
   `ThemeVariant` が `set_active_theme` 経由で正しく反映されること（コア単体
   テストでは「解決済み `ThemeVariant` を受け取った場合の挙動」までを検証し、
   OS 判定自体はプラットフォームレイヤ側のテストスコープとする）
6. **エラー時に panic しないこと**: `resolve_all` がエラーを返すケース
   （未定義参照・循環参照等、S2 §4.2 のエラー分類）で `set_active_theme` が
   panic せず `Err` を返すこと

  `#[non_exhaustive]` の付与や別列挙への置換要否を S5 実装時またはその後続
  Issue で検討する
- **部分キャッシュ無効化**: §4.3 のとおり、テーマ切替時の差分更新
  （変更キーのみ再計算）は本設計のスコープ外とした。S2 §7 と同じ理由
  （初期実装は全件再計算で構わない）で据え置く
- **OS 通知のプラットフォーム別実装詳細**: iOS（`NSAppearance` 相当）・
  Android（`Configuration.uiMode` 相当）・デスクトップ各 OS でのライト/ダーク
  変更通知の具体的な検出方法は、プラットフォームレイヤの実装詳細であり
  本文書のスコープ外とする（S16・プラットフォーム統合レイヤの後続 Issue）
- **`TokenResolver::new` の型名**: S2 文書のシグネチャ案 `ThemeId` に対し、
  トークン解決エンジンの型名は `ThemeVariant` を正とする（§2.2）
- **モジュール配置の表記乖離**: S1 §5.1 の `tokens/`（複数形）と S2 §4 の
  `token::resolver`（単数形）の乖離を本文書 §2.2 で `tokens::resolver` として
  解消したが、実際のディレクトリ構成は S3/S5 の実装判断に最終的に委ねる

## 8. セキュリティ考慮（OWASP Top 10 観点）

- **A03 インジェクション**: テーマ切替 API（`set_active_theme`）の入力は
  `ThemeVariant` の**閉じた列挙**に限定し、文字列によるテーマ名指定を公開
  API にしない。文字列由来の入力は S17/S18 の検証済み経路（§3.4）に限定する
  （S1 §5.2・S2 §3.2 の方針を継承）
- **A04 安全でない設計 / DoS**: テーマ切替は「キャッシュ全件無効化 → 全件
  再解決」を伴うため、高頻度切替（OS 通知の連打等）による計算資源消費の
  可能性がある。§4.2 の冪等契約（同一テーマへの切替は no-op）により、
  少なくとも「変化のない通知の連打」による無駄な再計算は防ぐ。差分無効化
  自体は §7 のとおり残課題とする
- **A05 セキュリティ設定ミス**: OS テーマ検出はプラットフォームレイヤの
  責務とし、コアが OS API・環境変数を直接読まない（§2.4・§3.3）。過剰な
  権限・依存を持たない構成を維持する
- **A08 整合性の不備**: 外部テーマ定義（S17）は「S17 読み込み → S18 検証 →
  解決エンジン」のデータフロー契約（§3.4、S2 §5.3 を踏襲）を経ることを
  本文書でも再確認し、未検証データがテーマ差分としてコアに入る経路を
  作らない
- **秘密情報**: 本文書に認証情報・内部 URL 等を含めない（create-commit
  スキルのシークレット検査対象）
- **メモリ安全性**: 本文書が設計するすべての型・API は `#![forbid(unsafe_code)]`
  の `fandhe-core` に閉じ、`unsafe` を要求する要素を持ち込まない
